● You're right. Nothing in the pipeline is truly indeterminate. Every
  asynchronous step is a promise or callback that the framework creates itself.
  Two things go wrong, and I've confirmed both in node:

  - Async work is invisible to the graph. It only knows about work through
    pending cells and effects queued inside a fit.
  - settle() can't see what it's waiting for. So it polls, and maxTurns is just
    a time budget measured in event-loop turns.

  Where async work escapes the graph

  1. async effects (the main one). docInjectEffect in FluidView.js is an async
     function. The effect wrapper does fn.apply(...) ?? true, so the effect's
     value becomes the returned promise. That counts as available as soon as the
     body starts.
     - So the whole load-and-commit phase runs untracked: the prepare fetches,
       Promise.all, link loading and the commit itself.
     - Test: I gave an effect a 200 ms await. settle() returned at once, with
       the body unfinished, the value a promise, and no open fits.
     - What stood in for tracking: only the side cell injDone, which finally
       sets to true. It only held work up because something happened to consume
       it: the gated layer release effects, and now hydrate's ready signal.
  2. Fetches with no consumer. fluid.fetch calls fetch itself and later calls
     set on a pending cell. While nothing pulls that cell, no fit contains it.
     - Test: settle() returned while a fetchText cell was still pending.
     - loadImportMap starts SFC fetches eagerly, before anything demands the
       layer (there's a TODO saying so). So pending fetches can exist with no
       consumer at all.
  3. Deferrals outside the graph:
     - fluid.invokeLater for history pushes in the array-mutation proxy, and for
       stepping async iterables in bindIterable.
     - The delay option of fluid.fetch.
     - Disposals deferred by stabilizeAsync and waitFor. This caused last turn's
       leaked fit: a watcher due for disposal was pulled one more time.
  4. DOM-originated events:
     - MutationObserver callbacks in liveQuerySelectorAll.
     - Stylesheet load/error in awaitLinkLoad.
     - DOMContentLoaded in applyOnLoad.

     Their timing is external, but each one is a wait we started, so we still
     know it's outstanding.

  Given that, "no effects queued and no fits open" is only a proxy for "done".
  It's correct only when every piece of async work happens to be visible as a
  pending cell consumed inside a fit. Hydrate passed with a large budget only
  because the injDone cells covered for case 1, and settle() kept polling until
  the I/O finished.

  What a closed-form answer looks like: a ledger of outstanding work, kept by
  the code that starts the work.
  - Register everything: the promises from async compute edges and async effects
    (FluidSignals.js, where it already branches on fluid.isPromise(result)),
    fluid.fetch, bindIterable steps, awaitLinkLoad, and invokeLater, which needs
    a tracked variant for framework use.
  - Signal changes: keep the count or set in a cell, so changes are visible
    reactively.
  - Fix async effects: make an async effect pending until its promise settles,
    rather than treating the promise as its value. That would also retire
    injDone as a workaround.

  settle() then becomes exact, with no turn count: stabilize, and if the queue
  is empty and the ledger is empty, it's done. Otherwise it waits for the next
  ledger entry to complete (Promise.race over the ledger, or waitFor on the
  ledger cell) and repeats.

  A genuine hang, such as a fetch that never returns, then shows up as an entry
  that never completes, which you can name by URL. A wall-clock timeout becomes
  the caller's policy, for example in hydrate.js, rather than something
  correctness depends on. Fit tracking can remain as the separate question of
  whether downstream effects have been honoured.

  The one thing the ledger can't cover is DOM events from outside the framework,
  like user input. Those aren't outstanding work, though: nothing is waiting on
  them, so they don't stop the graph from being settled.

  If you want, I can implement the ledger and pending-until-resolved async
  effects, and drop maxTurns from settle() and hydrate.js.

● Yes. They're the same mechanism: a one-shot effect on a cell that resolves a

  What the rows mean
  - The error row is a real bug in waitFor. On an error value it never settles,
    and it doesn't hold a fit open either. So settle() passes and
    pendingEffects() can't name it: a hang with no diagnostic. signalToPromise
    handles this correctly.
  - The fit rows match settle()'s design. Both hold a fit only while the source
    is pending, which is work inside the graph. An available value that doesn't
    yet satisfy the predicate is waiting on something outside the graph, so it
    correctly doesn't hold up settle(). So the predicate adds no new semantics;
    it extends signalToPromise cleanly.
  - The disposal difference doesn't matter. waitFor deferred its dispose for
    fear of disposing mid-pull, but signalToPromise has always disposed
    synchronously, and the suite passes. The deferral is what produced last
    turn's "disposed watcher pulled again" case, so synchronous is better. The
    filterPendingEffects fix stays either way.

  Recommendation: one implementation, fluid.cell.waitFor(cell, predicate = () =>
  true), built on signalToPromise's body:
  - a free effect,
  - reject and dispose on an error value,
  - return a pending value unchanged so its fit stays open,
  - when an available value passes the predicate, resolve and dispose
    synchronously,
  - otherwise return true.

● Here is the proposed waitFor. It replaces both current functions and keeps
  signalToPromise's semantics: a free effect, rejection on an error value, a fit
  held open while the source is pending, and synchronous disposal. The
  predicate is the only addition.

      /**
       * Resolve with the first available value of a cell which satisfies a
  predicate, or reject if the cell holds an
       * error. Whilst the cell is pending, the watching effect is itself
  pending, so that the fit in which it is pulled
       * stays open and fluid.cell.settle waits for it - this is work internal
  to the graph. Whilst the cell is available
       * but its value does not satisfy the predicate, the effect is not
  pending, since the awaited condition depends on
       * something outside the graph, e.g. a value delivered from an external
  timer.
       * @param {Cell} cell - The cell to watch
       * @param {Function} [predicate] - A test applied to each available value
  of the cell, which accepts any available
       * value if omitted
       * @return {Promise<Any>} A promise which resolves with the first
  available value satisfying `predicate`, and
       * rejects with the cell's value if it becomes an error
       */
      fluid.cell.waitFor = function (cell, predicate = () => true) {
          return new Promise((resolve, reject) => {
              const watcher = fluid.cell.effect(value => {
                  let togo;
                  if (fluid.isUnavailable(value)) {
                      if (value.variety === "error") {
                          reject(value);
                          watcher.dispose();
                      }
                      // Return a pending value unchanged so that the watcher is
  pending and holds its fit open
                      togo = value;
                  } else if (predicate(value)) {
                      resolve(value);
                      watcher.dispose();
                      togo = value;
                  } else {
                      togo = true;
                  }
                  return togo;
              }, [cell], {
                  isFree: true,
                  name: "waitFor " + cell.name + "/" + fluid.cell.fitId
              });
              watcher.get();
          });
      };

  Notes
  - No resolved guard. The watcher is disposed synchronously in the run that
    settles the promise, so no second run can reach resolve or reject. That's
    what signalToPromise already does, and the suite passes with it. Calling
    resolve twice would be harmless anyway.
  - Referring to watcher inside the body is safe. The effect's first run happens
    in watcher.get(), after the const is assigned. Creating the effect only
    queues it.
  - Other unavailable values. An unavailable value that is neither an error nor
    pending, such as the config variety of an unset cell, is returned unchanged.
    It doesn't hold a fit, because filterPendingEffects only counts pending
    values. That matches signalToPromise today.

  If you keep the name, signalToPromise becomes:

      /**
       * Converts a signal into a Promise for its first available value - see
  fluid.cell.waitFor
       * @param {Cell<Any>} valSignal - The signal to monitor
       * @return {Promise<Any>} A promise which resolves with the signal's first
  available value, and rejects if it
       * becomes an error
       */
      fluid.cell.signalToPromise = valSignal => fluid.cell.waitFor(valSignal);

  Otherwise it goes, and its callers are renamed: three in the framework, about
  14 in FluidSignalsAsyncTests.js, and the emitted text in lezer-transform.js. I
  haven't changed any code yet.

● Which effect duplicates injDone: it's the effect subscribeDocToInjections
  creates for each layer and document, docInjectEffect. Since the async-effect
  change, fluid.cell.awaitAsyncEffect keeps that effect pending for exactly as
  long as its async body runs. When the body finishes, the effect's value
  becomes true, because the body returns undefined and undefined ?? true is
  true. That is precisely injDone's contract: pending while injecting, then
  true. Currently injDone is a separate cell, set by hand in the body's finally,
  and its pending state only matches the effect's by convention.

  Differences to handle
  1. Before the SFC is parsed. injDone starts out pending. But docInjectEffect
     is non-free, so until the parse its value would be whatever injRecsSignal
     holds. readSFC initialises that to fluid.unavailable("SFC for ... is not
     available"), and fluid.unavailable defaults to the error variety. So
     without a fix, the effect would read as failed rather than pending, and
     waitFor on it would reject immediately.
     - The fix is in readSFC: give injRecsSignal a pending initial value, which
       is the honest state while the SFC loads.
     - One consequence: a subscribed SFC that never arrives keeps settle()
       waiting. It already would today, because injDone would never be set.
  2. When the body throws. The current finally sets injDone to true even on
     failure, so gated layers are still released. With effect pendency alone, a
     throw becomes an error value, and gated layers would never be released.
     - To keep the current behaviour, the body should catch and log. Failures of
       individual injections already come back as unavailable outcomes, which
       are logged and not fatal.
  3. Re-injection. injDone stays true once set, even when injection reruns, e.g.
     after the SFC text changes. The effect goes pending again on each run.
     That's more accurate: injectionsComplete and settle() then also cover a hot
     reload.
  4. Tags and diagnostics.
     - The layerName and dokkument tags that fluid.noteLayerInjectionInProgress
       reads move from injDone onto the effect.
     - I'd name the effect Injections for layer X, so pending reports from
       injectionsComplete, gateLayerOnPending and pendingEffects() stay
       recognisable. The specific message "Injection in progress for layer X"
       becomes fluid.pending's generic one, with the effect's name as its site.

      fluid.subscribeDocToInjections = function (layerName, dokkument) {

                      ).filter(injRec => injRec);
                      // Load phase - acquire all material, executing nothing
                      const prepared = await
  Promise.all(docInjRecs.map(fluid.prepareSFCElement));
                      // Commit phase - one synchronous block, so no
  stabilisation can observe a partial set of definitions
                      // Stylesheet links return promises which settle once the
  sheet is applied
                      const outcomes = await

                      outcomes.filter(fluid.isUnavailable).forEach(outcome =>
                          fluid.log(fluid.logLevel.FAIL, `Injection failure for
  layer ${layerName}: `, outcome));
                      console.log(`Injections for ${layerName} committed`);

                      Object.keys(oldInjRecs).forEach(nodeId => {
                          const newRec = injRecs[nodeId];
                          if (!newRec) {
                              fluid.clearInjRec(dokkument, nodeId);
                          }
                      });
                      oldInjRecs = injRecs;
                  } catch (e) {
                      // As for a failure of an individual injection, report it
  and complete, so that layers gated on
                      // this effect are released
                      fluid.log(fluid.logLevel.FAIL, `Failure injecting layer

  ${layerName}`});

● If get() stopped ending fits, reads would have no side effects. A fit would
  only end at stabilization, when stabilizeOnce calls endFits after draining the
  queue, so each fit would span a whole propagation instead of closing whenever
  someone happens to read a cell in it. You should then see far fewer,

  With auto-stabilization on, that's a microtask away, so code that relied on a
  synchronous read to close a transaction would only notice a slight delay.

❯ That seems attractive, and consistent with the "fully deferred stabilization"

● Yes, I think it's heading somewhere sound, with one refinement. The guarantee
  should be structural rather than temporal: a fit must be closed before the
  next transaction begins, not before anyone could look.

  Reads aren't the problem. get() is pull-based: updateIfNecessary recomputes a
  stale cell on demand. So a synchronous read in the middle of a fit already
  returns the fully propagated value for that cell, whether or not the fit has
  closed. Two things can actually go wrong in that window:
  - Side effects of reading. Today get() can end fits and run unrelated effects,
    as in the storeLayer case. Making reads pure removes this.
  - A new exogenous write. A set() arriving while the old fit's _consumedSources
    are still live would have its reverse-arc propagation wrongly culled. The
    incoherence you're pointing at is really this one.

  Don't try to win the scheduling race. You're right that the environment can't
  be made to guarantee our code runs first:
  - queueMicrotask is FIFO, so we can't jump ahead of microtasks other code
    queued earlier.
  - process.nextTick is node-only and on the legacy path, and has no browser
    equivalent.

  But JavaScript's run-to-completion model already gives us what we need.
  Nothing interposes inside a synchronous stretch, and every write enters
  through set().

  So enforce closure at entry, not by timing:
  - Reads are pure: get() never ends fits.
  - Fits end in one place: only stabilize() ends fits, after draining the queue,
    deferred or not.
  - An exogenous set() drains first. A set() made outside a stabilization
    synchronously flushes any stabilization already queued before starting its
    fit. stabilize() is now a cancellable, idempotent flush, so this costs
    nothing when nothing is pending. Writes made by effects during a pass are
    already folded into that pass.

  Then no write can observe a half-closed fit, and nothing needs to control the
  scheduler.

  What this asks us to define is which writes count as exogenous. In a system
  where every action is asynchronous, the line falls here:
  - Continuations of a fit: completion of async work issued within a fit, such
    as an asyncComputed resolving or an async effect's updateComplete. These
    must not start a new transaction. That's why pending effects hold their fits
    open.
  - New transactions: any other write, including one an async effect makes after
    an await in its own body.

  Overlapping transactions are a separate question. A new write can legitimately
  start its own fit while an older one is held open by pending I/O; "Fit
  decoupling … unrelated fit is active" tests exactly that. If both transactions
  touch the same bidirectional arc, that's a genuine conflict between
  concurrent transactions, and no scheduling fixes it. enlistInFit coalescing
  fits that share sources is the current, implicit answer.

  What this resolves: "values available for synchronous inspection at any time"
  stays true for values, because pull already guarantees it. What isn't
  synchronous is effects having run, and that's what stabilize()/settle() are
  for.
