  Feasibility, and the gap

  The ordering part works as the issue describes. Merging namespaced listener
  records happens in fluid.mergeLayerKey, and the existing
  fluid.parsePriority/fluid.sortByPriority handle before:/after: unchanged.

  The gap is that today an $effect has no value anyone else can read: effects
  are only created after the component is built, and nothing is stored at their
  path. So "a stable top-level construct which can be awaited on" needed one
  more step. I build a composite effect the way a $bindable is built: a cell
  stored at its path and run eagerly once the component exists. It is pending
  while the chain runs and then holds the final {$payload}. Other effects take
  it as an argument, and fluid.cell.settle() / fluid.cell.waitFor can await it.

  Where I departed from or added to the issue

  - An effect written as an array is always composite, even with one record. The
    issue says a single surviving record becomes a plain effect. I kept that
    only for effects written in simple form, so a consumer of {self}.readyMap
    doesn't break when a merge leaves just one record.
  - A listener that returns undefined passes on the payload it received. The
    chain stops at any listener that returns an unavailable value. If a run is
    overtaken by a newer one while it waits on a promise, it calls no further
    listeners.
  - {$payload} only works as a whole argument, not as {$payload}.path.
  - Behaviour change: before, two layers' {$effect: {...}} records were
    deep-merged, so their args arrays got combined element by element (a bug).
    Now the stronger one replaces the weaker as a whole. A test covers this.

  Changes

  - Fluid.js: fluid.collectEffectRecords merges listener records by namespace. A
    stronger record replaces a weaker one in place, and any value other than an
    effect replaces all weaker effects.
  - FluidIL.js: fluid.expandCompositeEffectRecord builds the chain, chosen in
    fluid.expandElement when $effect is an array. I also renamed the handler
    flag isBindable to isEager, since bindables and composite effects now share
    it.
  - FluidILTests.js: four new tests cover synchronous chains, merging across
    layers with priorities, simple-effect replacement, and async chains
    including awaiting the result and a run being overtaken. I checked that the
    merge tests fail without the merge change.
  - ../bagatelle/src/client/js/i6/libreMap.js: loadedMap, fillPatternsLoaded and
    styledMap are replaced by one composite effect, readyMap, with stages load,
    loadFillPatterns and applyStyle. Each stage now returns the map or a
    promise for it, instead of hand-building pending cells.
  - Other IMERSS files:
    - polygonDraw.js: I changed one reference to {libreMap}.readyMap.
    - BbeaMapTests.js: I added a test where a user record inserts a
      before:applyStyle stage and start-up is awaited.

  One thing to watch

  styledMap was onceOnly, and composite effects have no equivalent yet. If style
  or the fill-pattern settings changed at runtime, the chain would re-run and
  setStyle would wipe all sources and layers. Because readyMap still holds the
  same map object, the effects downstream wouldn't fire to add them back.
  Before, such a change was simply ignored. These settings are fixed in
  practice, but a onceOnly option for composite effects would be the follow-up
  if you want that guarantee.

● I've replaced fluid.makeEventFirer with a wrapper around a free fluid.event
  component whose listeners run through the new composite $effect.
  fluid.loggingEvent and fluid.failureEvent work on it unchanged for their
  callers. All 1876 framework tests pass, the four IMERSS i6 drivers pass (25 +
  65 + 49 + 12), and eslint is clean. Nothing is committed.

  How it works

  - The component: fluid.def("fluid.event") has the single member eventArgs.
    makeEventFirer constructs one, and the firer returned has just name,
    component, addListener and fire.
  - addListener(listener, namespace, priority): pushes a merge record onto the
    component holding dispatch: {$effect: [{namespace, priority, func, args: 
    "{self}.eventArgs"}]}. func wraps the listener and spreads the args back
    onto it. Records from separate pushes merge into one composite effect.
    Re-using a namespace displaces the earlier listener, and a listener without
    a namespace gets a unique one.
  - fire(...args): writes the args into eventArgs, then reads that.dispatch,
    which runs the listener chain synchronously.

  Changes I had to make to your design

  - eventArgs holds the args inside a small wrapper record, not as a bare array.
    The framework expands an effect's arguments by recursing into plain arrays.
    fluid.fail is often passed unavailable values, and expanding those would
    make the whole firing unavailable, so the failure would be silently
    swallowed.
  - Listeners only run inside fire(). Adding a listener rebuilds the component,
    and the composite effect runs as soon as it's rebuilt. Without a guard,
    every addListener would replay the last firing.
  - Exceptions are caught and rethrown from fire. The framework turns an
    exception inside a cell into an unavailable value, which would stop
    fluid.builtinFail from throwing. The wrapper catches the exception, stops
    the remaining listeners, and fire rethrows it.
  - There's a fallback option for re-entrant firings. The framework logs while
    it rebuilds the logging component, and a nested firing can't be dispatched
    through the cell that is already running. The logging fallback is
    fluid.doBrowserLog. The failure fallback is logFailure plus builtinFail,
    which is what fluid.fail already did before the event existed.
  - The two events are now created at the end of FluidIL.js, because they need
    the component system. Before that point, fluid.log writes straight to the
    console and fluid.fail uses its existing pre-setup path.

  Removed

  removeListener, soft namespaces, the namespace stack, preventable and promise
  events, and listeners given as global names. Listener return values are
  ignored. Also gone from Fluid.js:
  - fluid.event.identifyListener, impersonateListener, sortListeners,
    resolveListener, nameEvent, firer, addListenerToFirer, resolveListenerRecord
  - fluid.nameComponent, fluid.fireEvent, fluid.expandImmediate,
    fluid.mergeListeners, fluid.eventFromRecord, fluid.mergeListenerPolicy,
    fluid.makeMergeListenersPolicy, fluid.validateListenersImplemented,
    fluid.arrayConcatPolicy

  None of these had callers outside Fluid.js except fluid.fireEvent. Its one
  call, an afterDestroy notification in fluid.doDestroy, was already a no-op and
  is removed too.

  Tests and harness

  - qunit-fluid.js: expectFluidError used to add and then remove two failure
    listeners. It now adds only captureActivity, which displaces the previous
    call's copy and stays installed. I dropped the no-op "QUnit" listener.
  - FluidJSTests.html: now loads FluidIL.js.
  - FluidJSTests.js:
    - The soft-failure and log-interception tests restore the framework
      listeners by adding them again under the same namespaces.
    - Two tests only exercised removal and the namespace stack, and they're
      replaced by tests of:
      - a namespaced listener displacing an earlier one
      - an exception halting dispatch and being rethrown
      - re-entrant firing going to the fallback
  - fqunit-node.js needed no change: it creates onAllTestsDone with
    makeEventFirer() and only fires it.

  Cost

  One firing with 3 listeners takes about 60 µs (measured over 20,000 firings,
  with no spurious dispatches). That's far slower than the old direct loop. With
  logging on it adds up: the full test run went from 12.0s to 13.6s. It doesn't
  matter for failures, but it's worth knowing for logging-heavy runs.
