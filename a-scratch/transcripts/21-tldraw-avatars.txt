● No single limitation forces a hack in the main design. The broadcast linkage,

  The existing list

  - 5 ($bindable) is only half resolved, and it's the one that matters most.
    Updates now stream through a bound signal and unbind works. But a $bindable
    still never rebinds when its arguments change: it logs "Ignoring attempt to
    rebind". So hostBounds would go stale if a view's shapeId changed, or if
    tldrawHost were recreated with a new editor. Today neither happens, because
    each widget is built once per shape. A cleaner design would key the binding
    on its arguments: unbind the old value and bind again when they change.
  - 9 (conditionals only at component level) got worse after #19.
    closestNoteFinder's distance line is now a subcomponent holding a view
    subcomponent holding a template, just to show one line. That's design rather
    than a defect, but the nesting is now heavy enough that a short form
    deserves thought.
  - 13 ($for reconciles by index) is still unmeasured. The notes bridge has a
    related coarseness: it produces a whole new array whenever any note changes.
    So every note finder recomputes on any note edit, even if that note is far
    from all of them. Finer grain needs per-item collections, which is the same
    machinery 13 needs.
  - 7, 11 and 12 had no effect here. Holding the editor as a live object in
    tldrawHost read naturally.

  Fresh limitations found in this work and not fixed

  1. Avatars are only safe by luck. Without an "inert" marker, an avatar relies
     on missing prerequisites to stay quiet, and two cases don't depend on any:
     - A $linkage, or an $effect with no unavailable arguments, at a widget's
       top level would run in its avatar too. A linkage there would register
       globally.
     - An avatar of a fluid.resolveRoot layer would put itself into root scope
       and could displace the real component.

     Also, avatars count towards fluid.unavailableComponents, so using them
     server-side would block hydration from ever reporting that the page is
     ready. None of the current widgets trigger any of this. If inert is out,
     some standard opt-out is still needed, perhaps a layer the avatars area
     applies that the effect scheduler respects.
  2. Avatars are never destroyed. One stays alive per layer ever inspected. The
     member name is the layer name with dots swapped for dashes, which could in
     principle collide.
  3. Avatar introspection only sees raw configuration. I read the merged layers
     (flatMerged), not proxy[$u]. Reading through the proxy gives an unavailable
     value whenever any layer is unavailable, so it's useless for the "inspect
     even when instantiation fails" purpose. As a result, a preferredSize
     written as a $compute would be seen as the raw record, not its value.
  4. The SFC registry isn't reactive. The dropdown still re-reads it on
     pointer-enter. On first render a layer that's still loading is silently
     left out (that's the race I fixed). A reactive registry listing, combined
     with avatars, would make the list live.
  5. Linkages are global. The tldrawHost linkage applies to every top-level
     widget on the page: avatars, widgets outside the canvas, and widgets under
     a second editor if there were one. A linkage scoped to part of the
     component tree would be cleaner. Registering one also invalidates every
     component bearing the input layer.
  6. Shape lifecycle is still driven imperatively from React. InfusionHost
     builds and destroys components in useEffect. The clean form would be a $for
     over the store query of Infusion shape ids, but React owns the DOM
     containers. There's no way for Infusion to receive a container from a host
     renderer reactively, so component-per-shape can't be written declaratively.
  7. PTF reconstruction merges the root potentia shallowly ({...rootPotentia, 
     ...options.potentia}). The host-supplied view record replaces any
     transmitted view.$component wholesale. That's harmless now that shapeId
     lives there and is meant to be replaced, but any user view configuration in
     a transmitted widget would be lost.
  8. A component with no document waits indefinitely for an SFC. After my fix it
     waits for another component to load the SFC into a document, which is
     better than crashing, but it can wait forever. There's no notion of a
     default document.
  9. Functions are captured when a $compute is expanded. Replacing a global
     function, as I tried when instrumenting the probe, doesn't reach existing
     computes. This matters for live editing of a layer's plain-JS helper
     functions.
  10. One anomaly I didn't explain. In the probe, an effect over
      fluid.getForComponent(shadow, "hostBounds") never fired, although
      $computes reading {self}.hostBounds updated correctly. That's either a
      misuse on my part or a gap in how a site reference ($sitedRef) carries
      notifications through a reference into a subcomponent's bound cell. It's
      worth a small node test before relying on effects over such sites.
  11. Absent host data has two meanings. hostBounds defaults to null in
      fluid.topLevelWidgetView, so widgets must handle null, while tldrawHost
      members are unavailable outside tldraw. As a result closestNoteFinder's
      "Not placed on a canvas" branch can't actually appear, because
      {tldrawHost}.notes is unavailable first. Choosing one convention for this
      would tidy things up.

  If I were to pick the next work: rebinding of $bindable on argument change
  (5), an opt-out for avatars (1), and scoped linkages (5 in the fresh list)
  would remove the main fragilities. A reactive layer registry (4) would then
  make the dropdown fully declarative.

  $bindable

    really change. The new fluid.isEquivalentValue judges this:
    - components count as equal if they are the same component, whatever proxy

    member read without going through a write proxy is now the merged layer

  - fluid.avatar(layerName) creates an ordinary component holding just that

    fluid.def(), this includes layers and members inherited from parent layers
    or added by $linkage, and it updates reactively when layers are redefined.

  - Unbinding fixed: the unbinder was never actually called. A bare {boundValue}
    argument now receives the bound value as returned (e.g. a signal), and a
    bare function is accepted as bind/unbind.
  - Rebinding: a bindable now rebinds (unbind, then bind) whenever its arguments
    are notified with a fresh value, just as $compute re-runs.
  - onceOnly: true: binds exactly once until disposed, whatever happens to the
    arguments, including transient unavailability.
  - Binder dependencies: the binder runs untracked, so its dependencies are only
    its declared arguments.
  - Streaming: confirmed that readers see through a bound signal and receive its
    updates.

  - expandLayer now only copies a plain-object member when something inside it
    was expanded, so unchanged members keep their identity across turnover.
  - Each argument of $compute, $effect and $bindable is flattened in its own
    cell (fluid.flattenedArgCells), so an unchanged argument no longer re-runs
    its reader.
  - A component's root proxy now lives on its shadow, so it keeps its identity
    across turnover.
  - Effect: a member-reading $effect re-ran on every turnover at HEAD (3 runs
    over two turnovers in my probe) and now runs once.

  - fluid.mergeLayers records which layer sub-objects went into each merged
    object.

● Here is that block from my earlier review of remaining limitations, copied out
  as it was:

  1. Avatars are only safe by luck. Without an "inert" marker, an avatar relies
     on missing prerequisites to stay quiet, and two cases don't depend on any:
     - A $linkage, or an $effect with no unavailable arguments, at a widget's
       top level would run in its avatar too. A linkage there would register
       globally.
     - An avatar of a fluid.resolveRoot layer would put itself into root scope
       and could displace the real component.

     Also, avatars count towards fluid.unavailableComponents, so using them
     server-side would block hydration from ever reporting that the page is
     ready. None of the current widgets trigger any of this. If inert is out,
     some standard opt-out is still needed, perhaps a layer the avatars area
     applies that the effect scheduler respects.
  2. Avatars are never destroyed. One stays alive per layer ever inspected. The
     member name is the layer name with dots swapped for dashes, which could in
     principle collide.
  3. Avatar introspection only sees raw configuration. I read the merged layers
     (flatMerged), not proxy[$u]. Reading through the proxy gives an unavailable
     value whenever any layer is unavailable, so it's useless for the "inspect
     even when instantiation fails" purpose. As a result, a preferredSize
     written as a $compute would be seen as the raw record, not its value.

  Three later changes bear on it:

  - More reason to be careful with point 1: fluid.defaultDocument now lets an
    avatar start loading and injecting a not-yet-loaded SFC into the page.

    driver's awaitLayer had to learn to ignore the pending placeholder.
  - Binders are untracked now: any effects or bindables an avatar does run no
    longer pick up dependencies from reads inside their binders.
  - Still open: none of the avatar points above has been addressed yet.

  Inert flag

  Shadow.inert is documented on the Shadow typedef and at each place it takes
  effect. A component inside an inert one inherits it at construction, and the
  avatars area is marked inert, so avatars and everything they construct are
  inert. An inert component merges, expands, builds its subcomponents and
  evaluates any $compute that is read, but:
  - it allocates no $effect or $linkage and renders nothing;
  - a $bindable on it never binds, even when read (bindables are evaluated
    lazily, so reading one could otherwise trigger the binder);
  - it isn't put into root scope even if it bears fluid.resolveRoot;
  - it isn't tracked for availability;
  - traversals that start outside it, such as fluid.queryILSelector or
    fluid.visitComponentChildren, skip it;
  - the substrate tree filters on it.

  A new test covers these. With the flag switched off, the checks for effects,
  linkage, bindables, root scope and traversal all fail.

  A computed preferredSize

  No proxy change was needed. A missing prerequisite (e.g. {tldrawHost}) makes
  only the members that depend on it unavailable; the avatar stays available, so
  fluid.avatar(layer).preferredSize returns the computed value through the
  ordinary proxy. The driver now reads it that way.

  I tried a separate reader that went through the instance rather than its
  availability gate, and dropped it. A $compute over {self}.width is unavailable
  whenever its component is wholly unavailable, because {self} itself is gated
  on availability. A wholly unavailable avatar is one whose layers haven't
  loaded, and there's nothing meaningful to compute then. fluid.avatarMerged
  remains for the raw merged structure, e.g. checking $layers.

  Avatar deletion and naming

  - Deletion: fluid.deleteLayer now calls fluid.destroyAvatar(layerName).
    Fluid.js has a stub that FluidIL.js overrides, following the existing
    fluid.ensureImportsLoaded pattern. Otherwise avatars persist and track
    redefinition.
  - Naming: the member name is now the layer name itself, since path segments
    are escaped when composed into a path. This removes the dot-to-dash
    collision risk; avatar paths look like avatars.fluid\.demos\.storyTime.

  The suggested architecture

  It's intelligible and plausible. The current proxy does three jobs:
  1. It turns signal-valued members into plain values on read.
  2. It sends writes to the live layer.
  3. It follows data back to its source ("fish upstream").

  Infusion already declares dependencies explicitly through IL references, so
  reads don't need to be tracked to discover them. The pieces exist: sitedRefMap
  is in effect a path-keyed table of signals, shadowMap holds per-path
  metadata, and fluid.setForComponent is close to a single write gateway. Under
  that design the data would be plain objects, each path would have its own
  revision cell, and writes would go only through the gateway.

  The costs are real:
  - Writes: a plain self.x = 1 would mutate without notifying anyone, so every
    write would have to use the gateway.
  - Laziness: computed values would have to be put into the data, eagerly or on
    demand, so some of today's laziness would be lost.
  - Unavailability: unavailable values would need a representation in plain
    data.
  - Fish upstream: following data back to its source would need its own
    mechanism.

  It deserves its own issue. For the preferredSize problem, nothing so large is
  needed; the existing proxy already serves.

  Found, not fixed

  - fluid.trackComponentAvailability passes the availableInstance cell rather
    than its value to updateAvailability, so fluid.unavailableComponentMap is
    never populated for any component. Server-side hydration relies on it.
    Fixing it could change when hydration treats a page as ready, so I left it
    for you to decide.

    help diagnose a hydration that never becomes ready.

    when first read. Before, its initial null would have been trusted until the
    map first changed.

  component to be available; before, that part of the check was always

  out. The todo-list-sfc demo in the hydrate test has no such component.
