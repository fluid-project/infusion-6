  ## 1. Sibling folding

  "Next to" happens after merging. Layers are merged deterministically in
  priority order first. Then, if the merged value at a member such as `view`
  contains a `$component` key, all its other keys are spread over the
  `$component` record.

  So it is deterministic, but I can't defend it. The sibling always wins,
  whatever its layer's priority. A weak layer's `view: {template: B}` beats a
  stronger layer's `view: {$component: {template: A}}`: the result depends on
  how the config is spelled, not on priority. I agree it should go.

  Reverting it doesn't remove the turnover problem in section 4, though.
  Whenever `view.$component` is merged from more than one layer,
  `fluid.mergeLayers` builds a fresh object. The record then changes identity on
  every parent turnover, so the view is re-pushed.

  ## 2. Other members on the principal

  There are none. Every framework view layer (`viewComponent`,
  `templateViewComponent`, `sfcTemplateViewComponent`, `selfTemplate`,
  `selfTemplateRoot`, `partialViewComponent`, `viewComponentList`) contributes
  only `view`. `fluid.sfcViewComponent` contributes nothing. The principal also
  has `fluid.component`'s `events` and `destroy`, which aren't view-specific. I
  checked this by reading the definitions, not by listing a live component's
  keys.

  ## 3. Moving all view layers onto the view

  What would break:
  - **No layer accumulation.** C3 resolves only a component's top-level
    `$layers`. Inside a nested `$component` record, `$layers` is a plain array,
    and `fluid.mergeLayers` lets the last writer win. Combinations that work
    today would clobber each other:
    - `filters.withAssignee` combines `sfcTemplateViewComponent` with
      `partialViewComponent`.
    - The `select` subcomponent in `filterCompleted.vue` combines `UISelect`
      with `selfTemplate`.
    - The `@id` template record would overwrite whatever view layers the child
      defines.

    This is the serious one, and it's the same gap folding was papering over.
    We'd need either a union policy for nested `$layers` (another merge special
    case) or views whose variety is expressed only through members.
  - **Co-occurrence.** `fluid.viewComponentList` needs `viewComponent` and
    `componentList` on the same component, and they'd be on different
    components.
  - **Tag checks move to the view.** Substrate's `displayLayers`, the partial
    check in `activateTemplate`, `filterForSelfEditing`, and the partial
    detection in `sfcToInjRecs` would all need updating. IL selectors such as
    `"fluid.viewComponent"` would match views rather than principals.
  - **The MIME tag.** `fluid.sfcViewComponent` marks the *layer* as SFC-derived,
    so it should stay on the principal. Its name is part of the naming mess;
    something like `fluid.sfcLayer` would fit.

  If we go this way, I'd name the view layers consistently: `fluid.view`,
  `fluid.templateView`, `fluid.sfcTemplateView`, `fluid.selfTemplateView`,
  `fluid.partialView`, `fluid.listView`.

  ## 4. The exact sequence behind the self-dirtying

  I traced it with both signals fixes disabled, in the multiClass test after
  `that.b = false`:

  1. The write upgrades `b` into the live layer. Marking propagates to the
     principal's `flatMerged` and on down to the principal's own dependents.
     **Nothing reaches the view.** The view depends on its parent only through
     an imperative `pushPotentia` *write* inside the parent's `computeInstance`,
     which is not a graph edge.
  2. The view's `renderView` effect is queued through `{$parent}` in its vTree
     compute. In `updateIfNecessary` it refreshes `{self}.container` and
     `{self}.vTree` in order. The view's `availableInstance` and `flatMerged`
     look clean, so both are marked clean.
  3. Refreshing the vTree compute evaluates its `{$parent}` argument through
     `flattenSignals` and pulls the principal's computer. The principal now
     recomputes:

     `computeInstance → expandLayer → expandComponentRecord →
     pushSubcomponentPotentia → pushPotentia → potentia.set(...)`

  4. That `set` marks the view's `flatMerged`, `availableInstance`, and the
     `{self}.container` / `{self}.vTree` references `Dirty`. These are sources
     the effect has already refreshed.
  5. `findDirtyEdge` requires clean sources, so it finds none.
     `updateIfNecessary` then unconditionally marks the effect `Clean`, and the
     notification is lost.

  The stale vTree in the conditional-rendering test is the same chain one level
  down. The compute reads `{self}.templateTree` before `{$parent}`, and pulling
  `{$parent}` writes the view's potentia while the compute is still tracking.

  **Alternative.** Make the dependency a real edge. One line in
  `fluid.flatMergedComputer` does it: `shadow.parentShadow?.computer?.get()`
  before reading `shadow.potentia`. The principal's change then propagates to
  the view through ordinary marking, and any pull of a view member brings the
  parent up to date first. In a scratch copy with **both signals changes
  removed**, every IL, view, SFC, PTF and todo-demo test passes (only my two
  synthetic signals tests fail, as expected).

  The browser demo's old known issue (the first `inspectingSite` write
  re-instantiating the editor) comes back, though. So my signals fix was masking
  another write-during-evaluation path that the parent edge doesn't cover. The
  `@id` template record, pushed into a child from the parent view's vTree
  compute, is the other remaining instance of the pattern.

  ## 5. The blog post and fully deferred stabilization

  The post doesn't discuss fits or multiple activations. It does say the graph
  reshapes itself during propagation, so the priority queue won't be monotonic,
  and that nodes with large influence on the graph should jump the queue.
  Component instantiation is exactly such a node.

  The phenomenon isn't an artefact of the synchronous stack; it's semantic. A
  write during evaluation, with no edge behind it, dirties things the scheduler
  believed were settled.
  - **Today:** the loss comes from bookkeeping that assumes no new dirtiness can
    appear during a pull: `_isQueued` suppressing re-queueing, the unconditional
    `Clean` at the end of `updateIfNecessary`, and the early return while
    `_trackingRecord` is set.
  - **Under one update per reactive stack frame:** a queue-based scheduler that
    marks a cell clean when its activation *starts* would record the re-dirty as
    a new entry. The lost notification would become a second activation of the
    same cell within the fit, after a first activation that ran on stale inputs
    (a glitch). My rerun fix is a synchronous emulation of that. So I agree it
    isn't wrong a priori, and the deferred design would make it structural
    rather than patched.
  - **What deferral can't do:** stop the wasted, glitched first activation. That
    needs the edge, so the scheduler knows the parent's instantiation must
    precede the child's dependents.

  So the parent edge is the principled fix for ordering, and engine tolerance of
  re-dirtying is a separate robustness property that fully deferred
  stabilization would supply naturally.

  **3. The two options:**
  - **Nested-`$layers` accumulation policy.** Several layers each contribute
    `view: {$component: {$layers: [...]}}`. Today `fluid.mergeLayers` lets the
    last array win, so earlier contributions are lost. The policy would combine
    the arrays and then resolve the view's layer list through the hierarchy as
    for any component. Yes, this is FLUID-5614 exactly: gradeA declares `sub`
    with gradeC, gradeB extends gradeA and declares `sub` with gradeD, and
    gradeC disappears. The JIRA page says it was fixed in 4.0 but not how. The
    fault is latent in Infusion 6 already: any `$component` record whose
    `$layers` arrives along two paths drops layers.
  - **Member-only view variants.** This is what the code does now. Every view
    has the single layer `fluid.view`, and the variety comes from *members* that
    the principal's layers contribute into `view.$component` (`templateTree`
    computations, `elideParent`, `relativeContainer`…). Members merge key by key
    with ordinary priority, so nothing is lost. The cost is that the principal
    keeps layers whose only job is to contribute those members, and tag checks
    like `partialViewComponent` and `viewComponentList` stay on the principal.

  So "no layer on the principal" needs the accumulation policy, which means
  solving FLUID-5614 for Infusion 6. Member-only variants avoid that, at the
  price of the principal-side layers you found haphazardly named. A middle path
  would be to keep member-only variants but rename the principal layers
  consistently, for example `fluid.viewComponent`,
  `fluid.templateViewComponent`, `fluid.sfcTemplateViewComponent`,

  **What our failure is.** The chat calls `computeInstance` "an effect disguised

  the parent's `computeInstance` runs `pushPotentia`, a "cod write" in the
  chat's terms, onto the view's potentia. That write lands on sources the same
  pass had already validated, and the effect is dropped. The chat cites Solid
  2.0's `REACTIVE_MISSED_WAKE` (#3037) for precisely this: "a pass writes to a
  link that the same pass had already validated, so the node is rerun at the end
  instead of the wake being silently lost". The reverted signals fix was a
  synchronous version of that latch.

  **Your stack-frame question.** The chat's risk #1 answers it: fully deferred
  stabilization "protects effects from glitches, but it doesn't make a stale
  read safe". The problem splits in two:
  - **The extra activation is inherent.** A write that invalidates something
    already read needs another activation of the reader, however updates are
    scheduled. That matches your expectation of multiple activations of a cell
    within one fit.
  - **The loss belongs to the synchronous pull.** Our engine does record the
    read: `markStale` reaches the effect through its observer list. The wake is
    then discarded by bookkeeping that assumes nothing new can be dirtied during
    a pull: `_isQueued` suppressing re-queueing, and the unconditional `Clean`
    at the end of `updateIfNecessary`. A queue that marks a cell clean when its
    activation *starts*, and re-enqueues it on any later mark, would provide the
    latch structurally. With effects held until the queue is quiescent, the
    first, stale `renderView` would never reach the DOM.

  **What the parent edge corresponds to.** The nearest match is Solid's
  projection firewall. It carries an ordering obligation: before a projection
  serves a value, its derive must be brought up to date *without the reader
  subscribing*. Our edge has to subscribe, because in a pull model an
  unsubscribed child is never marked stale and so never pulls its parent. The
  chat's longer-term shape would replace the edge. Two of its ideas apply:
  - **Declared channel.** The parent owns its subcomponents' records, so
    `pushPotentia` is a write the parent is entitled to make. It would be staged
    for the next iteration coordinate rather than applied mid-pass.
  - **Stratification.** Instantiation is an allocating, non-monotone step, so it
    runs after merging has settled. Within that stratum, parents come before
    children, which can be read off the component tree.

  The parent-to-child dependency is then a "moral" one, known from addressing
  alone. The one-line edge is its literal-graph stand-in until that scheduler
  exists. Even then, the latch is still needed for reads that happen before a
  staged write is applied.

● Yes — it addresses the same problem, and by a better version of the mechanism
  I had in mind. Rather than unioning arrays during the parent's merge, Infusion
  4 **declines to merge subcomponent records in the parent at all** and lets the
  child's ordinary hierarchy resolution do the accumulating.

  **How Infusion 4 does it** (from `Fluid.js` and `FluidIoC.js` on `main`):
  1. **No merging in the parent.** The root merge policy gives `components` (and
     `dynamicComponents`) `fluid.deferringMergePolicy` with `noexpand`. For each
     key, each grade's record is *pushed* onto a `fluid.mergingArray`, so all
     contributions survive unmerged, in priority order.
  2. **A "light merge" of the scalars.** `fluid.lightMergeRecords` takes only
     the members needed before construction (`type`, `createOnEvent`,
     `source`/`sources`), each last-wins. All the records stay in `toMerge`.
  3. **Each record becomes its own merge block in the child.**
     `fluid.registerConcreteSubPotentia` tags every record `recordType:
     "subcomponentRecord"` (priority 700, between defaults and user), and
     `fluid.expandComponentOptions` makes a separate block from each one.
  4. **Grades accumulate in the child.** `fluid.computeDynamicGrades` walks all
     the blocks and concatenates each block's `gradeNames`, so gradeC and gradeD
     both survive. Plain options merge across blocks by priority, which also
     covers the later comment on FLUID-5614 about plain options corrupting along
     two paths.
  5. **It was a basic solution, as you said.** The line you linked notes that
     `componentDepth` "is currently unused but will be incorporated in
     mergeBlocks sort for refined versions of FLUID-5614". Ordering between
     records from different nesting depths was left unrefined.

  **How it maps onto Infusion 6.** Half of it is already there.
  `fluid.flatMergedComputer` takes the union of `$layers` across *all* of a
  component's merge records plus its `layerNames`, and resolves that through the
  hierarchy. A child given several subcomponent records would accumulate their
  layers already. The gap is upstream: `fluid.mergeLayers` fuses the per-layer
  `view: {$component: ...}` contributions into one object, and arrays are
  last-wins, before the child ever sees them. So the port would be:
  - **Collect, don't merge.** When `fluid.mergeLayers` finds a `$component`
    record at a key in any layer, it collects that key's contributions with
    their source layer and priority, instead of recursing. Infusion 4 could key
    this off the fixed `components` namespace; we have to detect `$component` at
    any member. A layer with a plain object where another has a `$component`
    should probably be an error.
  - **Light merge `$for`/`$if`.** These are our `type`/`createOnEvent`/`source`
    equivalents and need deciding before construction.
  - **Push one subcomponent merge record per contribution.**
    `fluid.expandComponentRecord` would push each one with its priority and its
    source layer as `mergeRecordName`. The child's C3 resolution then sees every
    contributed `$layers`, and its members merge with their own priorities
    rather than the parent's flattened ones. Provenance comes for free, so
    `filterForSelfEditing` could read a template's source layer directly.

  Two consequences matter for our current problem:
  - **Turnover churn largely goes away.** The contributed records are the
    original layer objects, stable across parent turnovers.
    `fluid.mountSignalRecord` can compare the list element by element and skip
    the re-push when nothing changed. Today's fused record is a fresh object on
    every merge, which is what turns the view over on every parent turnover and
    set up the missed wakes. The parent edge stays, for record changes that are
    real.
  - **It unblocks moving `fluid.viewComponent` onto the view.** With
    accumulation in place, `filters.withAssignee` can contribute `$layers:
    "fluid.partialViewComponent"` to `view.$component` alongside the base SFC's
    `fluid.sfcTemplateViewComponent`. The `@id` template record becomes just
    another record, and the principal needs no layer at all.

  What's still open:
  - **Where the record list goes.** Infusion 4's `componentDepth` caveat becomes
    ours, since a grandparent's `@id` template record and the parent's own

● The cause is a difference between DOMs rather than something random: linkedom
  and Chrome write out a node's attributes in opposite orders. Both failing
  tests are $if tests: "Conditional rendering" (short-form $if) and "Conditional
  rendering with long-form $if record". The $for test passes in Chrome. The
  same 4 assertions also fail on a clean export of HEAD, so this was there
  before #19.

  Cause
  - fluid.patchAttrs (src/framework/core/js/FluidView.js) applies a node's
    template attrs first, then its defaultAttrs. Here the template gives
    class="assignee", and fluid.assignContainerId adds the default
    id="fl-id-<path>".
  - Chrome writes attributes out in the order they were added, giving class then
    id.
  - linkedom 0.18.10 puts each newly added attribute at the front of the list
    instead. Adding title, id, alt comes out as alt id title, so under node you
    get id then class.
  - These tests compared container.innerHTML to a literal string with id first,
    which only matches linkedom's order. Other tests pass in both because their
    nodes have at most one attribute added this way.

  Fix (test-only, in tests/framework-tests/core/js/FluidViewTests.js)
  - I added fluid.tests.sortedInnerHTML(node), which writes out a node's
    contents with each element's attributes sorted by name.
  - The 4 assertions now use it, with expected strings written in sorted order
    (class then id).
  - I couldn't just re-add the attributes in sorted order and read back
    innerHTML, because linkedom would reverse them again. So the helper builds
    the string itself.

  If you'd rather fix this in the renderer, I can make it add the default id
  before the template attributes, so Chrome writes id first. The test would
  still need an order-independent comparison, because linkedom would reverse
  that order too.
