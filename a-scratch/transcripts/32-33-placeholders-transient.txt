**Why it fixes the problem**

- **One member, one meaning.** A layer supplies `vizFile: "placeholder://hortis.beaVizLoader/viz"` as its default. A fixture uses that default unchanged, and an app replaces it with its real data, as pages already do with `vizFile`.

- **Forgetting the override is visible.** A placeholder URL is marked by its protocol, so the framework can tell when one is fetched. `build.js` (or `copyOut.js`/`hydrate.js`, given a flag for app pages) can fail on any `placeholder:` fetch. **What the design has to settle**

1. **Where resolution happens.** Something must turn `placeholder://…` into a fetchable URL before `fetch()` sees it. I'd do it explicitly through a framework function such as `fluid.resolveUrl`, applied where a component computes its `fetchUrl`, rather than by patching global `fetch`. That keeps it declarative and visible to the hydrater.
2. **What backs the resource.** A layer declares its placeholder resources, either inline in its SFC (e.g. a `<placeholder name="viz" src="...">` block or embedded data) or as a file next to it. That gives a registry keyed by layer name and resource name. A Blob URL is the right result for inline or generated material. For a file, resolving to the file's own URL relative to its module is simpler, and it's what the `fluid.module.resolvePath` edits already do. I'd support both, with Blob as the backing for inline material.
3. **URLs derived from the URL.** `viz.detailsUrl` builds the details file's URL with `new URL(details.file, url)`, and that can't resolve against a `blob:` base. Either a placeholder resource must be self-contained (no details file), or resolution must keep a base. Self-contained is the simpler rule.
4. **Layer inheritance.** The layer named in the URL should be the one that declares the resource. `hortis.blitzVizLoader` would declare its own `placeholder://hortis.blitzVizLoader/viz` rather than resolving through its parent layers.
5. **Node and hydration.** Blob URLs are ephemeral and belong to one page. They must never be written into markup, which holds for data URLs here, and they should be revoked when their component is destroyed. I'm not certain Node's `fetch` accepts `blob:` URLs from `URL.createObjectURL`, so that needs checking. If it doesn't, the server side can resolve to the backing file or bytes directly.
6. **copyOut.js.** Because the registry is declarative, `copyOut.js` can list the placeholder files of the layers a page demands. Inline resources need nothing copied.

## What the upgrade relies on today

In `fluid.pathToLive` (`FluidIL.js:1106`), the live layer object is already mutated naively by `fluid.set(shadow.liveLayer, segs, cell)`. The potentia copy then forces three things:

1. **A cache miss in the merge.** `flatMergedComputer` keys its memo `shadow.lastMerge` on `[potentia, dynamicMergeRecord, resolved.mergeRecords]` by identity. A fresh potentia object is what defeats the memo.
2. **A fresh merge product.** `mergeLayerRecords` produces a new `flatMerged`, which now holds the cell at that path, and a new `layerMap`, whose `[$m].source` at that path is now the `live` record.
3. **Instance turnover.** `computeInstance` builds a new instance, re-runs `transferShadowMap` and `expandLayer`, which runs `markSignalised` for the new cell, disposes the layer's effects, and increments `instanceId`.

## The invariants involved

**I1. Merge products are immutable values of their inputs.**
- `lastMerge` hands back `previous.flatMerged` on a memo hit.
- `expandLayer` puts merged sub-objects into the instance by identity (the "keeps its identity" branch, `FluidIL.js:3052`).

So `flatMerged` and `layerMap` are, in effect, shared and frozen.

**I2. An instance's shape is fixed for its `instanceId`.** Which members are signals and which are plain values, and the `shadowMap` marks derived from that, are computed once per turnover. The marks are `signalised`, `hasSignalChild` and reactive roots.

**I3. A plain member changes only through instance turnover.** This is the one everything else rests on.
- A reader of a member gets a `$sitedRef` from `fluid.getForComponent`, computed by `getThroughSignals(shadow.computer, segs)`.
- If the value at that site is plain, the reader's only dependency is `shadow.computer`.
- Proxy reads of plain members work the same way.

So any reader may treat a plain member as a constant for the lifetime of the instance.

**I4. Provenance is correct.** `layerMap[…][$m].source` answers "which layer supplies this site". It is read by:
- `fluid.layerForSite`, used by the editor;
- `fluid.renderSite`, whose result `setForComponentImpl` records as `layerName` in history entries;
- the `reactiveLiterals` and `fallback` lookups.

**I5. A change in what the merge is fed causes re-merging and turnover.** There is already a precedent for an exception: once a path is live, writes change its value by `cell.set` without any re-merge. So in practice I5 holds only for the live layer's *shape*, not its values.

The moral argument is that the live layer is notionally total. Every member has a latent cell holding its merged value, and the upgrade only *materialises* one. Materialisation is harmless only if no observer can tell it happened. The value is identical at that instant, which is what `pathToLive` ensures, but that is not enough. **I3** is where it would show: every existing reader is bound to the old value as a constant, and would never see the writes that follow.

## Consequences for each observer, if we skip the re-merge

| Observer | With naive mutation (patch `flatMerged`, `layerMap` and the instance in place) | What would be needed instead |

## My assessment

"Upgrade without re-merging" is coherent only as *unobservable materialisation*. That needs three new pieces:
- a dependency per member, so that I3 becomes "a plain member changes only through turnover **or its own shape cell**";
- a live-shape version among the merge inputs, so the memo can't revert the shape;
- provenance updated and made observable.

Doing the patching by naive mutation would break I3 and could break the memo, and either would show up as silently stale bindings or lost writes. Those are exactly the failures turnover exists to prevent.

The alternative I listed earlier as option 2 bends **none** of these invariants: **create live cells at merge time for the plain-valued top-level members of a component**. The shape is then fixed when the instance is created, the first write is just `cell.set`, and provenance says `live` from the start. The cost is a cell for each such member whether or not anything writes to it. That could be narrowed to members that are declared, or to user components. I'd recommend option 2 unless that cell cost proves significant. The finer-grained invalidation that option 1 needs is close to making every member reactive anyway.

## Gating the scope ticks

**What happens today:**
- `fluid.cacheLayerScopes` (`FluidIL.js:368`) mounts a `scopeEffect` that reads `shadow.computer.get()`, so it re-runs on every instance turnover.
- It then **unconditionally** bumps its own `ownScopeTick`, and its parent's too.
- Each child's `scopeTick` is computed from its own tick plus its parent's own tick. So a root turnover ticks every child of the root.
- The readers of those ticks then re-run:
  - each `resolveContext` cell;
  - each live IL selector, through `fluid.visitComponentsForMatching`, which reads the `scopeTick` of every descendant it visits.

**Why gating is sound:**
- Scope entries are `{value: shadow, priority}`, and `resolveContext` returns `resolvedRec.value.computer`. Both the shadow and its computer cell keep their identity across turnover.
- IL selectors match against context names and member names (`fluid.matchILSelector` takes `contextHashes` and `memberNames`), and those come from layer names and member names.

So a turnover that leaves a component's applied contexts unchanged (the names, the shadows they resolve to, and their priorities) cannot change anything that tick readers observe.

**The gate:** in `scopeEffect`, compare the applied set with the previous one, and bump the own tick and the parent's tick only if it changed. The same goes for the `resolveRoot` bump of the root. The structural bumps on attaching and detaching children (`FluidIL.js:445`, `463`, `465`, `512`, `2433`) should be checked to be real changes too, but they aren't on the turnover path.

## What turnover costs once the ticks are gated

From the saanich instrumentation and the code:
- **One re-merge:** only the upgraded component's `flatMergedComputer` does real work.
- **Children aren't rebuilt.** At 9.72 s, the children's `flatMergedComputer`s re-ran because the root's `computeInstance` changed, but no `computeInstance` followed for any of them. Their `lastMerge` memo hit.
- **`$compute` and `$effect` cells are reused.** `fluid.mountSignalRecord` hands back the old product for an identical signal record.
- **Component arguments keep their identity.** The root proxy is held on the shadow ("keeps its identity across turnover"), so `{self}` and `{storyPage}` arguments compare equal.
- **Member reads are per member.** A read through the proxy goes through `getForComponent`, so it depends on that member's cached `$sitedRef`, not on the instance.
- **`$sitedRef` re-evaluation is cheap.** Every cached `$sitedRef` of the component depends on `shadow.computer`, so each is re-evaluated, and that is cheap. `expandLayer` keeps the identity of unchanged merged material, so each is cut off by equality. The only ref whose value actually changes is the one at the upgraded path, where a plain value becomes a cell. That is exactly your "changed provenance" set, already selected by cutoff.

  A precise lookup in `sitedRefMap`, replacing the dependency on `shadow.computer`, would only save re-evaluating the others. That's a later optimisation, not something correctness needs.

**What still costs anything is outputs whose identity isn't stable,** and those are the scope tick's consumers:

## A per-cell `equiv`

**What exists now:** one global policy, `fluid.cell.equals = fluid.defaultEquality`. It isn't pure reference equality: it already allows a relative tolerance for numbers. It's used in three places:
- `notifiableChange`, for an ordinary update;
- the early-cutoff comparison of a pending cell's `staleValue`;
- `cell.set` (`FluidSignals.js:1062`).

**The proposal:**
- A construction option `fluid.cell(v, {equiv})`, used in all three places in place of the global.
- An IL spelling for it, e.g. `$compute: {func, args, equiv: "hortis.qdl.sameQuery"}`.
- Library helpers such as `fluid.equiv.elementwise` (identity of each element).

**The semantics that matter:** when `equiv` says the values are equal, the cell **keeps its old value** and notifies nothing. Merely committing the new value without notifying would not do. Keeping the old value gives identity stability downstream for free, and that is exactly what `sameAsLast` emulates by handing back `last.value`.

**What it would cover:**
- **The scope tick.** `ownScopeTick` could become a cell holding the applied-context snapshot, with an entrywise `equiv`. The gate then needs no special-case code. The tick is written with `.set`, which is why `equiv` must apply to `set` as well.
- **Live IL selector results,** with elementwise identity.
- **`hortis.sameAsLast` and `hortis.lastValues`.** These would be replaced by `equiv: (a, b) => hortis.qdl.canonical(a) === hortis.qdl.canonical(b)` on the `predicates` compute. That removes the WeakMap keyed by component and name. It also behaves correctly across turnover, because the compute cell itself survives (`mountSignalRecord`).
- **Not `hortis.selectObs.memo`.** That is a cache that avoids re-executing a query, not an equivalence. `equiv` could take over its cut-off role but not its saving role, so it should stay, or move into `hortis.queryCache`.
- **`$oldValue`.** It only reaches the legacy `fluid.processSignalArgs` path, which is why it connects to nothing; modern `$compute` goes through `fluid.cell.mapSignalArgs`. It serves a different need: a reducer that builds on its previous result. `equiv` decides notification, not computation. So I'd either wire `$oldValue` into `mapSignalArgs` for reducers, or remove it. It isn't needed for either problem here.

**The caveat:** an `equiv` is a promise by the cell's author that no reader can observe the difference between the two values. A too-loose `equiv` drops real changes silently. It also has to be cheap, since it runs on every update; `qdl.canonical` is fine.

3. Port `hortis.obsFilters.predicates` to `equiv`, delete `sameAsLast` and `lastValues`, and decide what to do with `$oldValue`.

It needs four structures: a per-head registry of live queries, one match set per query, a per-head count of unavailable components, and a version cell per query.

## What a match depends on

These facts, from the code, define what has to be tracked:

- **`fluid.matchILSelector`** tests each selector element against the **own** scope of a component on the chain from the head down to the candidate: `scopes[thatpos]` is an `ownScope`, checked with `hasOwnProperty`. It ignores the head itself (`i = 1`) and everything above it. So a component's match depends only on the applied contexts of itself and its ancestors below the head.
- **A query also reports unavailability.** If *any* component in the subtree is unavailable, the result is unavailable, whether or not that component would match. So availability is a second input.
- **Results come in pre-order traversal order,** following each `childComponents` in insertion order. Consumers such as `filterComps` may depend on that order.
- **The traversal skips some components:** those without `that`, inert ones (when the head isn't inert), and ones already visited by `$id`, which guards against cross-injection.

## Data structures

| Structure | Where | Contents |
|---|---|---|
| `shadow.liveQueries` | the head's shadow; it replaces the cached cells in `shadow.queryILMap` | `Map<key, LiveQueryRecord>`, with the key being selector plus flat flag, as now |
| `LiveQueryRecord` | per query | `{parsed, flat, matches: Set<Shadow>, version: Cell<Number>, result: Cell}`. `result` is computed from `version`, sorts `matches` into traversal order, and has `equiv: fluid.equiv.elementwise` |
| `shadow.unavailableBelow` | the head's shadow | `Set<Shadow>` of the unavailable components in its subtree, shared by its queries |
| (no global registry) | — | a changed component finds its affected heads by walking up `parentShadow` and checking for `liveQueries`. That costs O(depth), at most about 6 here |

## Operations, and where they hook

1. **Creating a query** (`fluid.liveQueryILSelector`, `FluidIL.js:180`): fill `matches` with one full traversal, using the existing `fluid.queryILSelector` machinery, and fill `unavailableBelow` the same way. *About 40 lines.*
2. **A component's contexts change** (`scopeEffect`, `FluidIL.js:368`, wherever the new gate finds `changed`): for each ancestor head with live queries, re-match the component, and also its descendants if any of that head's selectors has more than one element. Its stack and scopes are rebuilt by walking up to the head. Each matching query's `matches` gets the component added or removed, and its `version` is bumped. A newly appearing component arrives here through its first `scopeEffect` run, so attaching needs no hook of its own. *About 50 lines.*
3. **A component is destroyed or detached** (the `delete …childComponents[…]` sites at `FluidIL.js:604` and `:2441`): remove it and its descendants from the `matches` and `unavailableBelow` of each ancestor head, and bump the versions. *About 20 lines.*
4. **A component's availability changes** (the existing per-component `trackComponentAvailability` effect): add it to or remove it from `unavailableBelow` at each ancestor head, and bump that head's query versions when the set changes between empty and non-empty. *About 25 lines.*
5. **Producing the result:** a computed cell on `version`. It returns the merged unavailable value if `unavailableBelow` is non-empty. ## Shared traversal per head: sketch

The idea: each head component keeps **one** traversal of its subtree, shared by all its live queries. Each query then only filters that traversal's entries with its own selector. Semantically nothing changes: it's the same traversal, the same matcher and the same dependencies, just done once per head rather than once per selector.

**Size:** about **60 lines of code plus ~25 of JSDoc in `FluidIL.js`, and ~60 lines of tests.**

### Data structures

| Structure | Where | Contents |
|---|---|---|
| `shadow.queryIndexMap` | the head's shadow, beside the existing `queryILMap` | up to two index cells, keyed `""` for a deep traversal and `"!"` for a flat one |
| index cell | per head and flat flag | computed by one `fluid.visitComponentsForMatching` walk, so it keeps today's dependencies on every visited component's `scopeTick` and `availableInstance`. Its value is `{entries: [{shadow, shadowStack, scopes}], unavailable}`: the visited components in traversal order with copies of their stacks, plus the merged unavailable value if any visited component is unavailable |
| live query cell (existing, in `queryILMap`) | per head and selector, unchanged in identity | now computed from the index cell alone. It returns `unavailable` if set, and otherwise filters `entries` with `fluid.matchILSelector`. It keeps the existing `previous`/`arrayEqual` cut-off |

The stacks must be copied: the walk reuses its `shadowStack` and `scopes` arrays, which are documented as not writeable. Each copy has one element per level of depth, about 6 here, so for ~520 components that's around 6,000 array slots per index rebuild. That's small.

### Operations, and where they hook

1. **`fluid.queryIndexFor(shadow, flat)`, new.** It finds or allocates the head's index cell. The traversal is the body of today's `fluid.queryILSelector`, minus the matching. *About 30 lines.*
2. **`fluid.liveQueryILSelector` (`FluidIL.js:180`)** filters the index instead of calling `fluid.queryILSelector`. *About 15 lines changed.*
3. **`fluid.queryILSelector`, the non-live one-off,** stays as it is, or reads an existing index when there is one. That's optional, about 5 lines.
4. **Disposal:** index cells live and die with the head's shadow, as `queryILMap` already does, so nothing new is needed.

Nothing else is touched: no hooks in `scopeEffect`, destruction or availability.

### Risks

Low. The results are identical by construction: the same walk in the same order, the same skips (inert components, no `that`, `visited` by `$id`), and the same matcher. The only new behaviour is that the walk happens once per head instead of once per selector.

There's one subtlety. A query that runs while the index is being recomputed must not see a half-built index. That's handled because the index is an ordinary computed cell, read only when complete.

### Expected gain

Measured now, the three queries at the root cost 124 + 65 + 61 = **250 ms** over 75 + 46 + 46 runs. That's about 1.4–1.65 ms per run, for walks of 403–520 components.

With a shared index:
- **The index rebuilds once per subtree change.** That's about 75–80 times, the union of the moments the three queries ran, at roughly the cost of one query's run, ~1.3 ms. That gives **~100–110 ms**.
- **Each query's filter** is a pass over ~520 entries with `matchILSelector`. That's a few `hasOwnProperty` checks per entry, without the cell reads the traversal makes, so I'd guess ~0.1–0.2 ms per query per rebuild. That gives **~25–45 ms** for three queries.

So the total would be about **130–150 ms**, a saving of roughly **100–120 ms**. That's about 40–50% of the selector cost, compared with ~90% for the incremental version.

The figure depends on how a run's time splits between visiting, which involves cell reads, and matching. I haven't measured that split. Profiling the time inside `matchILSelector` during a run would settle it in one trace.

### Compared with the incremental version

| | Shared traversal | Incremental |
|---|---|---|
| Code | ~60 lines (+25 JSDoc) | ~200 lines (+70 JSDoc) |
| Tests | ~60 lines | ~150 lines, plus a debug cross-check |
| Hooks outside the query code | none | `scopeEffect`, destruction, availability tracking |
| Risk | low: identical by construction | moderate: order, timing of attachment, a fallback for cross-injection |

The shared index is only a partial step towards the incremental version. The per-head registry carries over, but the index itself would be replaced by maintained match sets rather than extended.

## A sketch of `$transient`

`$transient` would be a declared member holding state that belongs to one component instance but takes no part in the reactive graph. Reading it creates no dependency, writing it notifies nothing, and it never upgrades a path to live, so a write never re-merges the component.

### Configuration

The simplest form gives an initial value, which is copied for each instance:

```js
fluid.def("hortis.resizeBar", {
    $layers: "fluid.viewComponent",
    // The drag in progress, if any - no business of the reactive graph
    drag: {$transient: null},
    ...
});

hortis.resizeBar.start = function (that, bar, event) {
    that.drag = {...hortis.resizeBar.startSizes(that, bar), startPos: event.clientX};   // no remerge, no notification
};
hortis.resizeBar.move = function (that, event) {
    const drag = that.drag;          // read untracked
    if (drag) { ... }
};
```

An optional `dispose` releases what the state holds, both when the component is destroyed and when the value is overwritten:

```js
fluid.def("saanich.timePeriodFilter", {
    // The timer applying the span once the handles have rested
    restTimer: {
        $transient: null,
        dispose: "window.clearTimeout"     // or a function; called with the outgoing value
    }
});
```

A structured scratch object can be mutated in place:

```js
fluid.def("bioreportr.lostPlants", {
    // Focus, caret, message and plant sought - kept apart from the signals so that typing doesn't redraw the gallery
    search: {$transient: {focused: false, caret: 0, message: null, sought: null}},
    // The latest card-loading run, superseding earlier ones
    run: {$transient: null}
});
// that.search.caret = 3 mutates the scratch object directly - it is handed out raw, never proxied
```

### Semantics

| Aspect | Behaviour |
|---|---|
| Read (`that.x`, or `{self}.x` in a record) | the current value, raw and untracked. Inside a `$compute`, this is almost certainly a mistake, so log a warning once per site: the computation won't re-run when the value changes |
| Write (`that.x = v`) | stored directly. It makes no live-layer upgrade, sends no notification and records nothing in the history. Any `dispose` is called on the outgoing value |
| Mutating in place (`that.x.y = v`) | allowed: the value is handed out unproxied |
| Turnover | **kept**. The holder belongs to the shadow, as the live layer does, so a re-merge doesn't lose an in-progress drag |
| Destruction | `dispose` is called on the current value, then the holder is dropped |
| Layer redefinition | the value is kept. The initial value is taken from the record only when the holder is first created |
| History, undo, hydration | excluded: it isn't serialised, isn't restored and isn't rendered |
| Merging | a stronger layer may replace `$transient` with a plain value, or the reverse. The strongest definition wins, as for `$reactiveRoot` |

### How the existing sites would look

| Current site | With `$transient` |
|---|---|
| `hortis.resizeBar.drags` (keyed by element) | `drag: {$transient: null}` on the bar component |
| `hortis.mfShell.presses` (keyed by grip element) | `press: {$transient: null}` on the shell |
| `saanich.timePeriodFilter.timers` | `restTimer: {$transient: null, dispose: "window.clearTimeout"}` |
| `bioreportr.traces.states` | `playback: {$transient: null}`, set when the timeline is created |
| `bioreportr.lostPlants.searches` | `search: {$transient: {...}}` |
| `bioreportr.lostPlants.runs` | `run: {$transient: null}` |
| `bioreportr.storyPage.keepRecord` | `keepRecord: {$transient: null}`, though see alternative 5 below |
| `bioreportr.storyPage.keepTaxon` | `keepTaxon: {$transient: false}`, likewise |

The two element-keyed maps become plain component members, keyed by the owning component rather than by an element.

### Implementation sketch

About 60–80 lines, plus documentation, in `FluidIL.js`:

1. **A record type.** `$transient` becomes an element type that `fluid.expandElement` recognises. Its handler produces a **holder**, `{value, dispose}`, mounted through `fluid.mountSignalRecord`. That reuses the old product when the record is the same, so the holder survives turnover with no new mechanism.
2. **The proxy's get handler.** If the member's `shadowMap` record marks it as a holder, return `holder.value` untracked, without going through `getForComponent` or `$sitedRef`. The same applies to reference resolution (`fetchContextReference`), which should also warn when the read happens inside a computation.
3. **The proxy's set handler and `fluid.setForComponent`.** Check for a holder before `fluid.pathToLive`. If there is one, call `dispose` on the outgoing value and store the new one. Writes to deeper paths (`that.x.y = v`) never reach here, because the value is raw.
4. **Disposal.** When the component is destroyed, call `dispose` on each holder's value. `fluid.disposeLayerEffects` or the destroy path in `computeInstance` would do this.
5. **Merging.** Treat `{$transient: …}` like other element records in `mergeLayerRecords`: replaced whole, never merged member by member.
6. **Tests:**
   - a value survives turnover;
   - a write doesn't notify or re-merge;
   - `dispose` runs on overwrite and on destruction;
   - a read inside `$compute` warns;
   - a nested mutation works;
   - layer redefinition keeps the value.

## Alternatives

**1. A per-component scratch context, `{$scratch}`.**
- A context name resolving to one plain object per component, held on the shadow and passed as an argument: `"$method:hortis.resizeBar.start({self}, {$scratch}, {0})"`.
- *For:* no new member type, and tiny to implement (about 20 lines in `fluid.resolveContext`).
- *Against:* the state is undeclared, so editors and diagnostics can't see what a component holds. Every layer shares one namespace, so two mixins can collide. There's no `dispose`.

**2. A framework-owned registry with no configuration, `fluid.transientState(that, key)`.**
- It returns a per-component `Map`, dropped on destruction, with optional `fluid.onDestroy(that, fn)` for cleanup.
- *For:* the smallest change to the sites. It's essentially today's `WeakMap`s moved into Infusion and tied to the component's lifecycle.
- *Against:* still invisible in configuration. It removes the smell only nominally: the state is still kept off to the side.

**3. State local to an effect.**
- An `$effect` record option such as `state: {}` gives the effect function a persistent object, like a ref that survives the effect's re-runs.
- *Good for* state used by a single effect: `traces.states` (the playback is driven by one effect) and the debounce timer.
- *Not for* state shared between several DOM handlers, such as the resize drag's start, move and end, or the search box's focus and caret.

**4. Purpose-built options instead of general state.**
- `debounce: 400` on an `$effect` (or `$method`) covers `timePeriodFilter.timers` outright, and the timer disappears from user code.
- A cancellable "latest run" helper for asynchronous loads would cover `lostPlants.runs`: each new run aborts or ignores earlier ones. It could be `fluid.latest(...)`, or an `AbortController` held by the framework.
- *For:* each one says what is meant.
- *Against:* it covers only those patterns, and the drag, press, search and playback state still need somewhere to live.

**5. Intent carried with the action (`keepRecord`, `keepTaxon`).**
- These are one-shot flags left by one action for another effect to find. The cleaner design passes the intent with the navigation itself, e.g. `storyPage.showPane(key, {keepRecord: id, keepTaxon: true})`. The clearing effect then reads it from the transition rather than from a side table.
- *For:* no state at all, and the cause and its effect sit together.
- *Against:* it's an application-level change to the navigation API.

**6. Reactive state with care, i.e. a `$reactiveRoot` member written untracked.**
- *Against:* every write still notifies readers and may upgrade a path to live and re-merge. That's exactly what these sites avoid ("so that typing doesn't draw the gallery afresh"). Not viable for high-frequency interaction state.

## Recommendation

**`$transient` as the general mechanism, plus two targeted pieces.**
- **`$transient`** covers drags, presses, playback, search and runs. It's declared, visible to tooling, has a lifecycle and survives turnover.
- **`debounce` on `$effect`** removes the timer pattern, which is common enough to name.
- **Intent carried with navigation** for `keepRecord` and `keepTaxon`, done in bioReportR rather than in Infusion.

`{$scratch}` is the cheapest option, but it reproduces today's lack of declaration. Effect-local state is a good companion to `$transient` rather than a substitute: I'd add it only if `$transient` turns out to be awkward for single-effect state.

**Where I departed from the inventory's plan:**
- **Effect history as `$transient`:** `placed` and `topSpeciesSelected` record what an effect has *done* (a `jumpTo`, a selection), not a function of their inputs. A reducer would misfire on unrelated re-runs.
- **`searchWidgets` as `$transient`:** it's made lazily after rendering and moved into each drawing. That makes it state, not a binding.
- **`keepRecord` and `keepTaxon` as `$transient`:** the cleaner alternative, carrying the intent with the navigation, is a change to the navigation API, so I left it.
- **Reducer inputs:** each reducer takes all of its effect's inputs, so it recomputes exactly when the effect used to run.

**Bindings now unbind:** a new `bioreportr.binding()` helper in `story.js` records each DOM or MapLibre listener and added element, and `dispose()` removes them. That fixes the listener leaks the old guards had: rebinding to a new map or document used to leave the old listeners attached.

**What I left alone:** group E (`qdl.derivedCache`, `qdl.indexCache` and `hortis.selectObs.memo`), as planned: they're caches keyed by immutable data. The local, non-global `WeakMap` at `libreMap.js:1312` is also unchanged.

**To bear in mind**
- **Saanich now needs the new Infusion.** Its code now relies on `$transient`, `debounce` and `{$oldValue}`, and bagatelle's client on `fluid.resolveUrl`. It will only work once a release of Infusion with these is vendored into saanich.
- **Howe Sound isn't updated.** Its copies of the shared bioReportR files haven't been touched; `copyFrameworkOut.sh` would carry the changes there.
- **Coverage:** I didn't exercise the Lost Plants search widget, or hover and tap on the map's areas and populations. Both depend on live iNaturalist data or real pointer input. Their code paths load without errors in all the scenarios above.
