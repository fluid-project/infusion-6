  What's done

  New file src/framework/core/js/FluidPTF.js. I added it to package.json (client
  and server lists, plus the test list), build.js, both FluidView test pages
  and the five demo pages that load FluidView-browser.js.

  - The format. fluid.ptf.encode / decode write and read MIME multipart
    documents.
    - Each part says what it is in its Content-Description (layer, potentia or
      live).
    - For a layer part, the Content-Disposition filename is the layer name. For
      the other two it's the path relative to the copied component: / for the
      component itself, /child for a subcomponent.
    - Lines are separated by plain LF so the text is easy to read and edit. The
      decoder also accepts CRLF.
    - fluid.ptf.isPTF(text) is a cheap check that tells a PTF paste apart from
      anything else.
  - Collecting. fluid.ptf.componentToPTF(component) walks the component and its
    subcomponents and gathers three things:
    - The definitions of the user layers in their $layers. SFC layers are sent
      as their original SFC text; JavaScript layers are written out as a
      fluid.def(...) call, with functions written out as their source.
    - The user potentia, with $layers holding the direct layer names.
    - Each live layer, flattened to a path → value map.

    Values that can't go into JSON, such as the container DOM node the host
    passes in, are dropped.
  - Rebuilding. fluid.ptf.instantiate(text, {potentia, overrideLayers}):
    - Registers any transmitted layers that aren't already defined. SFC text is
      loaded directly through a new fluid.loadSFCText.
    - Creates the component as a free component, with options.potentia merged on
      top so the receiving side can supply its own container.
    - Once the component is available, applies the live state.

    The tests round-trip an SFC component and a JavaScript component with a
    subcomponent. They rename the layer throughout the document before
    rebuilding, which also shows the format can be hand-edited.

  MIME type mechanism
  - Every layer loaded from an SFC now gets a fluid.sfcViewComponent tag layer
    added (in fluid.sfcToInjRecs), whether or not its $layers was written by

  - The editor now picks its mode layer from this through

  Limitations to know about

  - Pasting runs code. Rebuilding evaluates JavaScript layer parts with new 
    Function, and SFC parts inject their scripts, so a paste executes whatever
    code it carries. That's the same trust as loading an SFC from wherever the
    text came from, but it's worth deciding on deliberately.
  - JavaScript layers lose named global functions. If a layer refers to a global
    function by name (e.g. func: "fluid.foo.bar") and that function was defined
    outside fluid.def, it isn't included. SFC layers don't have this problem
    because their whole text is sent.
  - Copying a nested instance loses some config. Only "user" merge records are
    collected, and today only free components have them. Config that a
    subcomponent inherits from its parent's layer isn't sent.
  - Subcomponents created by templates or $for may not get their state back.
    Their parts are applied only if the subcomponent exists once the root is
    available. Any that can't be applied are listed in unresolved in the result.

  How it works

  tldraw 5.5.2 has two documented hooks that fit, so nothing in tldraw needs
  patching. They're passed through the options prop, from a new module
  demo/tldraw/js/tldraw-clipboard.js.

  Copy and cut (onBeforeCopyToClipboard)
  - If the selection includes any Infusion shapes, a plain-text PTF document
    goes on the clipboard instead of tldraw's compressed format.
  - The document contains a tldraw part holding tldraw's own copied content as
    readable JSON (positions, ids, bindings and any native shapes alongside). It
    also holds one nested PTF document per Infusion shape, whose filename is
    the shape id.
  - FluidPTF.js now supports nested multipart documents, as RFC 2046 allows.
  - For cut, the shapes are deleted by our code, because cancelling tldraw's
    clipboard write also cancels its delete.
  - Copies with no Infusion shapes are left entirely to tldraw.

  Paste (onClipboardPasteRaw)
  - Keyboard paste: the plain text is checked with fluid.ptf.isPTF, which can be
    done immediately. If it matches, each Infusion shape in the tldraw content
    is tagged with meta.ptfToken, a token pointing at its decoded parts. The
    content is then handed to tldraw's normal paste, so new ids and positions
    behave exactly like a native paste. InfusionHost sees the token and rebuilds
    the component with fluid.ptf.instantiateParts instead of creating a fresh
    one.
  - Bare component documents: a document from fluid.ptf.componentToPTF that has
    no tldraw part pastes as a single new shape.
  - Any other paste goes to tldraw unchanged.

    asynchronously, so we can't check for PTF before deciding. We therefore
    claim any menu paste containing plain text only, which is what our copy
    writes. If it turns out not to be PTF, it's pasted as an ordinary text
    shape. A plain URL pasted from the menu becomes text rather than a bookmark.
    Keyboard paste is unaffected.
  - Not tested with real key presses. In the headless browser I fired synthetic
    copy, cut and paste events, and called the menu hook directly rather than
    clicking the context menu. A quick manual Ctrl+C / Ctrl+V in a real browser

  - Deleting with the Delete key and then undoing still restores a component
