● I'd keep the todoList-style hoisting but put a small driver layer under it, so
  the same demo script can run in two places: linkedom (fast, in npm test) and
  a real headless browser (real hit-testing, :hover, layout). The script stays
  the same and only the driver changes.

  Why linkedom alone won't do

  The parts that regress most are the ones linkedom can't run:
  - Overlay positioning: fluid.getClippedBounds and fluid.applyOverlay
    (src/framework/edit/js/editorRoot.js:33, :216) depend on
    getBoundingClientRect and scroll offsets.
  - Hover: .fl-clickable:hover and similar rules are pure CSS. The mouseover →
    inspectingSite path in substrateTree.js:359 relies on e.target.closest(...)
    from a real hit test.
  - CodeMirror 5 needs layout before it will accept edits at all.
  - contenteditable editing of "Boz" needs real Selection/Range behaviour to be
    convincing.

  Hoisting alone would test the reactive plumbing (history records, layer list
  contents, propagation from editor to app) and miss everything visual.

  Proposed architecture

  demo-script (data)  ──►  runner (node, fqunit reporter)
                                │
                       driver interface: load / perform(step) / settle / query /
  screenshot
                        ┌───────┴────────┐
                linkedom driver     browser driver (CDP or WebDriver BiDi)
                        └───────┬────────┘
                     in-page agent: fluid.test.agent (plain JS, loaded into the
  page)

  1. The in-page agent does most of the work. A plain script loaded into the
  page does three things:
  - Resolves semantic locators to elements, e.g. {text: "Edit", role: "button"},
    {layer: "fluid.demos.substratePost", in: "layerList"}, {substrateSite:
    "..."}, {text: "Boz", within: {layer: "fluid.demos.footer"}}.
  - Waits on fluid.cell.settle(), so there are no sleeps. The cancellable flush
    from #17 helps here.
  - Evaluates expectations: element counts, text, classes, layer-list contents,
    history records, inspectingSite, overlay visibility.

  Because the agent runs in the page, a host only needs two primitives to be a
  driver:
  - evaluate JS in the page;
  - deliver native input at x,y, or a keystroke.

  That's what makes it portable. It works the same for Chrome, Firefox,
  Electron, a mobile WebView, or linkedom.

  2. Drivers
  - linkedom driver: reuse fqunit-html.js. Native input is replaced by synthetic
    events dispatched to the located element. CodeMirror edits go through the
    instance API. Steps marked requires: "layout" are skipped and reported as
    skipped, not passed. This runs inside npm test.
  - Browser driver: I'd start with no npm dependency at all:
    - Launch the system Chrome (/usr/bin/google-chrome is present) with
      --headless --remote-debugging-pipe.
    - Speak CDP as NUL-delimited JSON over file descriptors 3 and 4. That avoids
      needing ws, works on Node 16, and is roughly 150 lines.
    - Serve the repo with a tiny built-in http server. Under file://, Chrome
      blocks the fetch that fluid-module and fluid-import use.
    - Input.dispatchMouseEvent at the centre of the agent-reported rect triggers
      both real :hover and the framework's mouseover. Input.insertText handles
      typing into contenteditable and CodeMirror.
    - Page.captureScreenshot on failure.
  - Cross-browser later: if you want Firefox (which has dropped CDP), swap in
    puppeteer-core with its WebDriver BiDi mode. It drives installed browsers
    without downloading one. The driver interface stays the same, so the
    dependency stays optional. I'd avoid Playwright here because it downloads
    its own browsers and does more than we need.

  3. Script format. I'd make the steps data rather than trying to parse the
  Markdown prose. Each step keeps the human sentence, so demo-script.md can be
  generated from it, or checked against it:

  fluid.def("fluid.demos.composeEdit.script", {
      page: "%composeApp/index.html",
      steps: [{
          say: "Open the editing panel by pressing the Edit button",
          do: "click", target: {role: "button", text: "Edit"},
          expect: [{count: {in: "layerList", select: ".fl-layerlist-layer"},
  equals: 8},
                   {visible: {in: "substratePane", text:
  "fluid.demos.substratePost"}}]
      }, {
          say: "Hover a substrate row",
          do: "hover", target: {substrateRow: {layer: "fluid.demos.footer"}},
          requires: "layout",
          expect: [{overlayMatches: "target"}]   // overlay rect ≈ target's
  clipped bounds
      }, {
          say: "Edit \"Boz\" to read \"Booz\"",
          do: "editText", target: {text: "Boz", within: {layer:
  "fluid.demos.footer"}}, to: "Booz",
          expect: [{text: {within: {layer: "fluid.demos.substratePost"}},
  contains: "Booz"},
                   {historyTop: {layer: "fluid.demos.footer", op:
  "updateLayer"}}]
      }]
  });

  Writing it as a fluid.def lets a demo ship its own script, and other demos
  (tldraw, pell-edit) can reuse step layers. A plain JSON file would also work
  if you'd rather keep it outside the IL.

  Plan

  1. Write the agent: locators, actions, expectations and settle, using linkedom
     only. Port demo-script.md and get the non-layout steps green in npm test
     (with the todoList utilities folded into it).
  2. Add the CDP-over-pipe driver and HTTP server as a separate npm run
     test:browser. Turn on the requires: "layout" steps (hover, overlay
     geometry, CodeMirror via the keyboard) and add screenshots on failure.
  3. Optionally add the puppeteer-core BiDi driver for Firefox, and generate the
     Markdown from the steps.

  Open questions

  - Does the linkedom tier earn its keep? Running everything in the browser is
    simpler, but it pushes the editor tests out of the dependency-free npm test.
    I'd keep both tiers.
  - Exact overlay geometry will vary between environments by a pixel or two; the
    "off by a little" fudge in applyOverlay suggests this. Expectations should
    compare with a tolerance and not use pixel snapshots.
  - Stable hooks: some locators would be much easier with a few rendered
    attributes, e.g. data-fl-layer on each layer root. That's a small framework
    change worth making deliberately rather than relying on title or CSS
    classes.

  I can also write this up as a page to attach to issue #18 if that's useful.

  "Captive" means the same thing for all of them: a pinned browser binary
  downloaded once when the package installs. Nothing is baked into the npm
  tarball, so the first install needs network access and about 150–250 MB. After
  that, any machine with npm ci gets an identical browser, and the system
  Chrome is never touched.

  Recommendation: Puppeteer

  - Fully self-contained: npm ci alone gets the right Chrome, which suits an
    agent on an unfamiliar system. A .puppeteerrc.cjs can point the cache inside
    the repo (e.g. node_modules/.cache/puppeteer) rather than ~/.cache, so
    everything stays in the checkout.
  - Reproducible: each Puppeteer release pins one exact Chrome build, so pinning
    the npm version pins the browser.
  - The API matches the design above: page.evaluate drives the in-page agent,
    page.mouse.move produces real :hover and mouseover, page.keyboard.type
    handles CodeMirror and contenteditable, and page.screenshot covers failures.
    It also gives raw CDP access if needed.
  - Playwright has the nicer test runner, but the separate browser-install step
    is easy for an agent to miss, and it's more than you need with only one
    browser.
  - Electron is the interesting outlier. Because it bundles its own Node, the
    host's Node version barely matters. But on Linux without a display it needs
    xvfb (or a headless ozone flag that I haven't verified on these versions). A
    page inside Electron also isn't quite a plain browser page.

  The Node floor decision

  - The browser tier requires Node 18: use puppeteer@24.43.1. It matches this
    machine (18.15.0) and the repo's .nvmrc, and its Chrome is recent. This
    would be a devDependency for a separate npm run test:browser. The linkedom
    tier and the framework itself would stay on Node 16.6.2.
  - Strictly Node 16:
    - puppeteer@21.5.1 works, but its Chrome is about version 119/120. That's
      probably fine for testing framework logic, since nothing here needs new
      browser features, but it's frozen.
    - Alternatively, @puppeteer/browsers@1.9.1 could download a current Chrome
      for Testing, driven by the small zero-dependency CDP-over-pipe driver I
      described earlier. I believe 1.9.1 can resolve stable to a current build,
      but I haven't checked that.
  - Requires Node 22: use the latest Puppeteer, 25.14.0.

  I'd pick the Node 18 option. Your memory notes set the 16.6.2 floor for the
  node test drivers (from #12); does that also cover a browser-tier runner? If
  it does, I'd take the @puppeteer/browsers@1.9.1 route over the old
  puppeteer@21 so the Chrome doesn't go stale.

  Either way, the design from before holds: the in-page agent and the step
  scripts don't depend on Puppeteer. Puppeteer is just the browser driver, and
  the linkedom driver keeps running the non-layout steps in npm test.

  The two bugs

  - CodeMirror edits were discarded (fluid-editor.vue): writeText now looks up
    the SFC's text signal by layer name, instead of reading layerRec.sfcDef
    through the proxy, which turns it into a plain string.
  - No history for template edits (FluidView.js): if an SFC's text changes but

    history entry. Script edits still get their record from writeLayer. A new
    step that renames the post in its script checks that an edit produces
    exactly one record, not two.

  The inspect button

  Hovering already showed the right layer name and colour, but three things were
  broken:
  - Clicking did nothing. The hover pane ignores pointer events, so clicks went
    straight through to the app. While inspecting, a click inside the app is now
    intercepted before the app sees it, and the layer opens in the editor. The
    test clicks over the "2016 paper" link and checks that the tab opens and the
    page doesn't navigate away.
  - overlayClick turned off the wrong flag (inspect.inspecting instead of
    inspect.active), so inspect mode stayed on after a click.
  - The pane was 8px out of place. When the editor is docked, FluidEdit.css
    gives body contain: paint, which shifts where absolutely positioned elements
    are measured from. applyOverlay now measures the pane's real starting
    point, and the overlays use box-sizing: border-box. This also replaced the
    "somehow we are off by a little" fudge.

  Fixing the position exposed a fourth problem. The substrate row highlight now
  sits under the cursor, takes the mouseover itself, and flickers on and off. It
  now ignores pointer events too.

  Container ids

  A component's rendered container gets id="fl-id-<component path>" unless its
  template or the page already gives it one. The id comes and goes with the
  component's other attributes: when an $if turns off, the leftover empty <div>
  drops it. Four existing assertions that compare exact markup now expect the
  id, and a new test covers it. The ids also make stable test targets, e.g.
  [id$='.post.1.footer'].

  New test steps and runner features

  I added steps for substrate-row hover, inspect mode (hover over two
  components, click to open, no pane once inspect is off) and the script edit.
  The pane checks compare its position and size with the component's, and its
  colour with the layer-list entry. Run against the old code, these steps fail
  exactly as intended, e.g. pane at (473, 869) instead of (465, 861).

  The runner gained:
  - a hover action;
  - checks that one element covers another and that a style matches
    (matchesStyle), plus exact-text checks;
  - a --settle wait (default 250ms) so a check only passes once the page has
    stopped changing;
  - scrolling only when the target isn't already visible;
  - a knownIssue marker, reported as # TODO, which doesn't fail the run.

  The known issue (not fixed)

  The first time anything sets editorRoot.inspectingSite, the entire editor is
  rebuilt: menu, layer list, history, substrate and editor panes.
  fluid.pathToLive does this the first time a member is written, and declaring
  it $reactiveRoot doesn't help. In the test, the first substrate-row hover
  leaves the highlight about 1.5px out because the rebuild shifts the layout; a

  (IL) code, so I've left it for you to decide. The step will report when it
