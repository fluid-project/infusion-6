  How you write it: member: {$component: "{context}.path"}. A string in
  $component is now a reference to an existing component, which gets injected at
  that member instead of creating a new one.

  I used this form for every injection in the crossInjectView test, including
  the bare view: "{view1}.view" lines from the issue. A plain reference string
  at a member still means "a value", not an injection. Merging a bare string
  with $component records also still fails, with the existing "should be written
  as {$component: ...}" message. {view1} resolves from both the outer component
  and from view2 without needing {self}.view1.view.

  What injection does (fluid.expandInjectedComponentRecord, in FluidIL.js):
  - Records: the target goes into parentShadow.childComponents[member],
    pathToComponent at the new path, and the target's injectedPaths. The target
    keeps its original path, and its own subtree is not re-scoped.
  - Scope: the parent's children see the target under the same names it would
    have if it had been created there: its layer names, their nicknames, and the
    new member name. Its old member name is not added. This runs in an effect,
    so it updates if the target's layers change.
  - Withdrawal: the effect removes all of these entries if the reference stops
    resolving to that component, if the record changes or is disposed, or if the
    target is destroyed. In those cases the member becomes unavailable.
    Destroying the component that holds an injection leaves the injected
    component alone.
  - Proxy: reading an injected member returns the target's own proxy, so
    that.view === that.view1.view. I made this general: any member that resolves
    to a bare component is now proxied, as flattenSignals already did.

  Destroying $for components: calling destroy on a member of a $for component
  list now deletes its source data item, following references back to the
  original data in the same way as the delete proxy. The list then destroys the
  component. Every other component is still destroyed in place. Destroying a
  static subcomponent is left for the separate issue you mentioned.

  Override rule (worth a look): when a component's record merges from several
  layers, an injection discards every weaker contribution at that member. If a
  stronger inline record sits on top of an injection, only the records stronger
  than the injection are used. So in the test, view2's injection overrides the
  view record from fluid.tests.crossInject.second. One side effect: a user
  record that adds just {container} on top of an injection ends up as a
  component with no layers, so it is unavailable.

● I'd do it in two parts. The view2 case is easy and predictable. The outer case
  needs injection decided when the reference resolves, which is also where the
  risk is.

  1. A bare reference that merges with $component records (the view2 case)

  At the moment fluid.collectComponentRecords rejects any value at a member that
  is not a {$component: ...} holder. I'd let it accept a bare IL reference
  string there as well, and file it as an injection contribution, the same as
  {$component: "{view1}.view"}. The rest of the pipeline would work unchanged,
  because fluid.expandComponentContributions already treats a string
  contribution as an injection that overrides anything weaker.

  A non-reference value merged with $component records would still fail with the
  current error message. Whether a reference counts as an injection here is
  decided entirely during the merge.

  2. A bare reference with nothing to merge against (the outer view: 
  "{view1}.view" case)

  Here nothing in the configuration says a component is meant. Only resolving
  the reference can tell. So I'd handle injection at resolution time, for
  references at top-level members only:

  - Give plain references a proper record. Today fluid.expandElement returns
    fetchContextReference(...) directly for a plain reference. That product
    never goes through fluid.mountSignalRecord, so it is never reused or
    disposed when the parent turns over. Anything that registers an injection
    must be disposable, so I'd add a $ref-style entry to
    fluid.expandElementTypes. The reference would keep its value semantics.
  - Attach a "maybe" injector to top-level references. When segs.length === 1,
    the product gets the same injector effect as
    fluid.expandInjectedComponentRecord. That effect registers an injection
    while the reference resolves to a component, and withdraws it otherwise. I'd
    pull the effect out into a shared helper. A reference resolving to anything
    else stays a plain value, with no registration and no unavailability.
  - Never inject self or an ancestor. References like owner: "{todoList}" or
    "{self}" must not register, or the tree gets a cycle. The parent component
    would end up containing its own ancestor, and every tree walk and scope
    chain would have to defend against it.

  Risks to settle first

  1. Meaning change. Infusion 4 separated members: {x: "{y}"} (just a reference)
     from components: {x: "{y}"} (an injection). Infusion 6 has only one
     namespace, so this rule makes "any top-level member that resolves to a
     component" an injection. Before switching it on, I'd grep the demos and
     editor SFCs for top-level references that resolve to components, run the
     node and puppeteer suites, and see what changes.
  2. Scope pollution. Under the current rule, an injected component brings its
     layer names and nicknames into its new parent's children's scope. For an
     implicit injection that could quietly change how siblings resolve, e.g. a
     reference used only for convenience might start shadowing
     {fluid.viewComponent}. One option is to put only the member name into scope
     for implicit injections, which is enough to make that.view look like a
     real view subcomponent. Explicit {$component: "..."} would keep the full
     scope behaviour. I'd recommend this split, but it's your design call.
  3. Tree visibility. fluid.viewShadowFor, fluid.queryILSelector and the
     editor's tree walks all go through childComponents. Implicit injections
     would show up in all of them, which is the point for view but may be noise
     elsewhere. Limiting it to members that hold $component somewhere would
     avoid that, but it fails the outer case. That's why I'd fall back to
     limiting scope (point 2) rather than which members qualify.
  4. Cost. Each top-level plain reference would get an extra effect. Most of
     these resolve to plain values, so I'd keep the effect cheap: it does
     nothing until the resolved value is a component.

  Tests I'd add

  - Bare-reference versions of the existing crossInjectView assertions.

    no registration.
  - A reference to an ancestor, {self} or {$parent} is never registered.
  - A reference that changes from a component to a value and back registers,
    withdraws and registers again.

● I've reworked it so a reference becomes an injection only when it resolves to
  a component. The {view1}.view syntax from the issue now works as written, with
  no special form. All 1113 node tests and all 20 puppeteer demo steps pass,
  and eslint is clean.

  How it works now
  - Merge doesn't decide anything. fluid.collectComponentRecords treats a bare
    IL reference like any other value: if it's the strongest value at that
    member, it overrides weaker $component records. The merge doesn't try to
    work out whether it means a component. Other non-reference values mixed with
    $component records are still an error.
  - I removed the {$component: "{ref}"} form. It's now rejected with a message
    saying to write the reference directly. Everything goes through one path.
  - Resolution decides. IL references at top-level members are now mounted
    through mountSignalRecord via a new fluid.expandReferenceRecord, so they're
    reused and disposed when the parent turns over, which plain references never
    were before. A new helper, fluid.componentShadowForSignal, follows the
    reference's signal chain looking for a $component or $availableInstance
    signal, or a proxy onto one. If it finds one, the component is injected at
    that member, using the same register/withdraw machinery as before. If not,
    the member is just a plain value. Either way, reading the member gives what
    the reference resolves to.
  - Never injected: references to the component itself or an ancestor ({self},
    {$parent}, {/}, or something like "{todoList}" from inside a todo list),
    since those would make the tree cyclic. Nor is a reference that resolves
    back to its own path.

  What this showed about {view1}.view
  - The dotted form already worked. For "{view1}.view", the chain reaches
    view1's $component computer for its view member, so it's injected wherever
    it appears. That covers both of the issue's cases: overriding view2's own
    view record, and the outer component's plain member.
  - {view1} with no path did not. fluid.resolveContext returned the component
    instance, not its signal, so the chain hid that a component was there. It
    now returns the component's computer.
  - That change broke one caller. The event-binding code in FluidView-browser.js
    called target.get() and expected an instance. That broke the editor demo,
    which the node tests didn't catch but the puppeteer run did. It now uses
    fluid.deSignal(target), which also copes with {self}.

  Tests
  - The existing IL and view tests now use bare references.
  - New checks: references to plain values, {self} and {/} are not injected; a
    reference overrides a weaker $component record and is injected; a $component
    holding a string is reported as an error.

  Still open
  - Cost: every top-level IL reference now gets an injector effect and two
    computed cells. Early cutoff stops value changes from reaching the injector,
    but it is extra machinery on a common path.
  - Meaning: any top-level member resolving to a component is now an injection,
    and it brings that component's layer names into its new parent's scope.
    Nothing in the tests or demos regressed, but the scope point from my
    previous answer still applies.
  - Not fixed: fluid.flattenSignals tests deref.variety (should be $variety). As

● I didn't break the race. Nothing schedules construction so that {view1}
  resolves first; a reference that is evaluated too early simply fails and then
  gets re-evaluated once the name arrives in scope. And as far as I can measure,
  that doesn't cost any extra broken renders. The CodeMirror flash you've
  noticed happens at HEAD too, so it isn't caused by this change.

  How the race is handled
  - Scope is reactive. fluid.resolveContext reads the component's scopeTick.
    When view1 is instantiated, its scope effect writes its member name and
    every layer name and nickname into its parent's childrenScope, then bumps
    the parent's ownScopeTick. Any reference that failed earlier is re-evaluated
    within the same stabilization.
  - The merge doesn't wait for resolution. view2.view: "{view1}.view" overrides
    second's own view record when the records are merged, so no view is ever
    built at view2.view that would later need tearing down. Likewise the outer
    view member only becomes a view, through childComponents.view, once the
    injection happens.
