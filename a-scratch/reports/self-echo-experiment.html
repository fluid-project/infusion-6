Self-Echo Under Recomposition

The same CodeMirror layer editor, built in Infusion 6 and in React with Zustand, put through four recompositions, then rebuilt in a declarative Infusion style. The question is where the code that stops an editor hearing its own changes has to live, and what it costs to move things around it.

The question

Mainstream web applications are organised around one-way dataflow and read/write segregation. A component receives a value and a separate setter, and never writes its inputs directly. Issues of the kind Infusion handles with transactions and update sources rarely come up there by name. The question is why.

Ryan Carniato's article Two-way binding is a two-way street argues that two-way binding leaves state ownership unclear. He holds that frameworks should make it opt-in at least, and he prefers to avoid it altogether. The article offers little evidence beyond the experience of Angular.js:

Two-way binding can turn your code into an unpredictable mess, and that is not something you want to experience firsthand.Ryan Carniato, “Two-way binding is a two-way street”

Infusion 6 takes the other side. Any holder of a component proxy may write its state. Each write is a transaction (a fit) carrying the sources of the change. An effect can decline changes from a source with excludeSource, and the sources travel with the change through computations and through the writes made by effects (FLUID-5498).

Hypothesis under test The real cost of one-way binding is a loss of composability. Every site where mutation can occur has the capability injected into it. When the application is recomposed, that injection has to be rewritten across the application. Is this loss real or only apparent, and can applications written with mainstream idioms be recomposed straightforwardly?

The concrete case is the self-reactive cycle of a CodeMirror editor whose edits are validated asynchronously. Sketching it in a mainstream system shows that one-way dataflow doesn't remove the cycle. The cycle runs through the third-party widget, outside the framework's model, so it gets handled by hand at each widget. The experiment measures what that costs as the application changes shape.

The editor cycle

A user edits text in CodeMirror. The edit is validated asynchronously, here by a 150 ms check that the text is well-formed JSON. Valid text is committed to the store, and committed text flows back to every editor showing the layer, so that undo, other panes and file loads reach them.

flowchart LR
    U["User types in editor A"] --> V["Async validation, 150 ms"]
    V -->|valid| C["Commit to the store"]
    C --> T["Layer text"]
    T --> RA["Write into editor A"]
    T --> RB["Write into editor B"]
    RA -. "the echo: stale if A has been edited since" .-> U

The return path to editor A is the problem. Validation takes time, so by the time a commit arrives the user may have typed more. If the editor accepts its own stale commit, it overwrites the newer typing, and CodeMirror's setValue also moves the cursor to the start. Editor B, and editor A when the change came from elsewhere, must still receive the text.

How each side suppresses the echo

Infusion. The editor's read effect declares excludeSource: "self". The editor's own writes are stamped with its self source, the component's shadow, which can't be written in configuration or confused with another instance's. The source travels with the transaction to the commit, through the effect that makes it, and across the async validation, so the returning change is recognised by identity.

React and Zustand. The editor holds its own document as an uncontrolled widget. At first it keeps a ref holding the text it last committed and skips that text when it comes back from the store, which is equality rather than identity. When that stops working, the fix is to tag each draft with the editor's useId() and carry the tag through the store as textOrigin.

Method

Both apps use the same CodeMirror 5 build, the same validator and the same DOM contract. Each starts as a baseline (v0), and four recompositions follow, each applied to the previous version:

  1. R1. Add a second editor showing the same layer.
  2. R2. Move validation out of the editor into a shared service. Editors submit raw drafts, and the service commits each valid draft in turn, so history keeps every valid edit as before.
  3. R3. Redirect where the text is stored. Editor B edits a separate "notes" layer while editor A keeps the main one.
  4. R4. Insert a transforming step between commit and editors. The store keeps the committed text, and what editors and views show is its normalised form, JSON.stringify(JSON.parse(text)), which drops whitespace. A user's own spacing must never be rewritten under them.

Each recomposition was first made the natural way for its framework, then tested, then fixed if it failed. The measures are the non-blank lines changed per file, whether the reusable editor had to change, and how many attempts it took. A headless Chromium harness drives every version through the same checks:

commit
One valid edit is validated and committed. The editor keeps its text and cursor.
typingDuringValidation
Typing 3, then 4 60 ms later, then 5 after the first commit has landed but before the second. No keystroke may be lost and the cursor must stay put. One undo must return to the previous valid edit, so each valid edit was committed.
undo
Undo reverts the committed text and reaches the editors.
crossPane
With two editors on one layer, each one's edits reach the other, including typing during validation.
separateLayers
With two layers, editor B's edits and undo affect only the notes layer.
normalisedTyping
Typing , 3, 4 and 5 during overlapping validations. The editor keeps [1, 345] as typed while the committed text reads [1,345], and undo brings the normalised [1,34] back into the editor.

The harness proves it can see the failure. Removing the "self" exclusion from the Infusion baseline loses the last keystroke and resets the cursor, as listed under Controls. The layer text is a JSON array such as [1] rather than an object. Infusion configuration reads any string beginning with { as a context reference, and at the time had no way to escape one. A leading backslash now does.

R2 · Validation as a shared service

This is the recomposition the hypothesis is about, because it moves the commit away from the editor that suppresses its echo.

React. The direct translation moved the editor's equality ref onto draft submission. It failed. A stale commit of an earlier draft no longer matches the ref, which has moved on, so the editor writes the stale text into itself. The last keystroke is lost and the cursor goes to 0. The working fix tags each draft with the editor's useId(), adds a textOrigin field and origin parameters to setDraft and commit, and has the validator forward the origin. The store now has to know about editor identities.

Infusion. The editor's two echo-suppression lines stayed as they were, and only what the editor writes changed: a draft instead of a commit. The first attempt still failed badly, for reasons a user couldn't reasonably diagnose. Commits stopped after the first one, undo didn't stick, and the editor was overwritten. Finding the causes took instrumentation of the reactive graph, and they turned out to be four defects in the framework, listed under Framework defects. One problem was in the user code: the commit effect read the history it appends to with tracking. Wrapping the commit in fluid.cell.untracked fixed that. React has no counterpart to this hazard, because Zustand's getState() isn't tracked.

R3 · Redirecting where the text is stored

Both passed first time. In Infusion, the store became a component instantiated twice, and each editor's store reference was overridden in configuration at its instance site, leaving the editor file identical. The React editor had to change, because it imported the single store hook. A React baseline that took its store from context would have avoided that change, but only if someone had anticipated it. Infusion's redirection needed no such foresight.

R4 · A transforming step between commit and editors

React passed first time. The origin tag forced by R2 marks the change itself, so a transformed value still carries it. Infusion's first attempt rewrote the user's [1, 345] as [1,345] and moved the cursor. Two validations were in flight at once. When the earlier one settled, the computation stopped counting as pending, so its transaction closed while the later run was outstanding, and that later result arrived without its source. Before R4 the equality check in the editor hid this, because the result equalled the editor's text. Normalisation makes them differ. The defect was fixed in the framework, and the user code needed no change.

A declarative rebuild

The Infusion editor above followed an early pattern from the framework's own CodeMirror integration: the work happened in imperative code inside the binder, and the editor's commits were stamped by hand with fluid.cell.withAmbientSource. To check whether that shaped the results, the Infusion chain was rebuilt in a declarative style, after two framework changes. An $effect record may now declare source: "self", so that everything it writes carries the component's self source. A $method now runs its function untracked, so values a method reads never become dependencies of a computation or effect that calls it. Its arguments are still resolved in the caller's context, because they can be genuine dependencies of the caller.

In the declarative editor, the CodeMirror listener only records the raw edit in a member. An async $compute validates it, and an $effect declaring source: "self" commits it. In R2 that effect forwards the edit to the store as a draft instead, and the store's commit effect calls its commit method with no untracked. Every step passed first time, the client code makes no fluid.cell calls, and the two lines that suppress the echo are declarations that never change. The style costs about nine more lines than the imperative one.

The conclusions hold. Composability is slightly stronger, since the suppression is now declared rather than applied. The R2 hazard that only Infusion had, an effect re-triggering itself through a method's reads, no longer exists: the earlier control that omitted untracked now passes. The declarative chain was built on the fixed framework, so its first-time passes say nothing about how it would have fared before the fixes. It can't run on the earlier framework, which lacks source:.

The off-protocol control matters most for the hypothesis. React's origin tag is a convention that every code path writing the text has to honour, and a writer that forgets fails silently. Infusion's nearest equivalent mistake, forgetting untracked, now fails loudly with a message naming the fix.

Framework defects

Seven defects in the Infusion core surfaced. The first five appeared while building this small app the natural way. The last two appeared while trialling untracked method dispatch for the declarative rebuild: an early version of that change, which also resolved a method's arguments untracked, broke two compose-edit demo steps, and tracing the breakage found both. All seven existed before the experiment. Each is fixed in the repository, with a regression test confirmed to fail without the fix.

DefectSymptomFixTest
Lost re-staling An effect whose run made one of its own inputs stale was marked clean afterwards and taken off the queue. The input stayed stale with nothing to pull it, and the effect never ran again, so commits stopped after the first. A mark made during a cell's own update is kept (_restale), and an effect is taken off the queue before it runs, so it can be queued again (FluidSignals.js) “An effect whose run makes one of its sources stale is notified of later changes”, and the IL test “An effect writing members of its own component is notified of each later change, once”
Writing created a dependency The first write to a member made a tracked read, so an effect came to depend on what it wrote and ran twice The read in fluid.pathToLive is untracked (FluidIL.js) Covered by the IL test above
Unbounded self-triggering Once the first fix was in, an effect genuinely writing a value it reads looped forever An effect run more than fluid.cell.maxEffectRuns (100) times in one stabilization is reported through fluid.cell.reportCycle and not run again in that pass “An effect which cyclically triggers itself is stopped and reported”
Sources lost across async Only pending effects held a transaction open, so a pending async computation's result arrived with no source A pending async computation holds open a transaction that carries sources. A first version held every transaction and hung a bagatelle start-up test, so it is limited to sourced ones Exercised by the overlap test below and the R2 harness run
Overlapping async runs When an earlier promise settled while a later one was outstanding, the computation stopped counting as pending and the later result lost its source Outstanding promises are counted per cell (_inFlight), and a cell with any outstanding run keeps holding its sourced transaction “Sources are carried across an async computation whose runs overlap”
Stale computations after a binding A computation whose own pull made a source it had already received change, e.g. by making a binding, kept its stale value permanently A computation is re-marked only when the source that changed had already returned its value to the update in progress, and is then recomputed at once, with a bound. A first version, which re-marked on any change, broke 106 tests “A computation whose received source changes in the course of its update is brought up to date”
Sources left stale by a traversal While a cell's sources were brought up to date in turn, a later one, e.g. a binding that turned over a component, made an earlier one stale again. The cell then found no edge it could run and was marked clean without being recomputed. A reopened editor kept the previous layer's text The pass over an edge's sources repeats while any of them has gone stale and is not on the traversal stack, with a bound “A source made stale again whilst a later source is brought up to date is brought up to date once more”

Two smaller issues came up while building the baseline. Configuration had no way to write a literal string beginning with { or $. A leading backslash now escapes one, so "\\{" in JavaScript source stands for a literal {. The editors were also switched from {global}.CodeMirror to the global, in the belief that the argument arrived proxied. That was a misdiagnosis. The proxy was the unavailable value of the unescaped text, which CodeMirror took for a document object. A control with {global}.CodeMirror restored passes every check. After the fixes, the Infusion suites pass in full: 2129 tests in node, 349 in Chromium, 34 demo steps, and 151 in the bagatelle port.

What the evidence suggests

The composability cost is real, and it shows up as soon as the commit moves

In Infusion, echo suppression stayed as two lines inside the editor through all four recompositions, and the editor file was untouched in R1, R3 and R4. In React it moved into the store's data model and API at R2, as a field, two parameters and forwarding in the validator. The editor changed again in R3 and R4. This matches the hypothesis. The ability to recognise one's own change was injected at each place a mutation happens, and moving the mutation meant rewriting it in several places.

Equality is not identity

Suppressing an echo by comparing values works only while nothing on the return path transforms the value or lets it go stale. Both a shared validator (R2) and a normaliser (R4) broke it. The mainstream fix is to carry an identity in the data, a hand-built version of what Infusion's transactions carry automatically. Once React had it, R3 and R4 caused it no trouble, but it is a protocol every writer must follow.

Carniato's point about predictability held, given the framework's maturity

Every Infusion failure was a framework defect rather than a user mistake, five in total over four small recompositions, and each needed graph instrumentation to diagnose. Two more surfaced in the follow-up, again found only by instrumentation. React's failures were ordinary logic errors that could be read from the code. Infusion's code was also 40 to 50% larger. One difference has gone: Infusion no longer needs untracked where React's getState() needs nothing, since methods now run untracked.

On balance the evidence favours the architecture on composability and the mainstream on predictability. That judgement is about the framework as it stood. The defects are fixed, and the declarative rebuild passed every step first time on the fixed framework. The question to ask next is whether that holds on further recompositions, or whether a reactive graph that keeps write capability general keeps producing failures that need instrumentation to explain.

Limits

  • Both implementations were written by the same author, who also wrote the framework fixes. The choice of idioms on each side is theirs.
  • The React baseline used a single global Zustand store, which is the common idiom. A store taken from context would have spared the editor change in R3 if the redirection had been anticipated.
  • The app is small, and four recompositions are a small sample.
  • The harness relies on fixed delays around a 150 ms validator. It was stable across every run here but is timing-dependent.
  • The Infusion first-attempt outcomes in R2 and R4 reflect the framework before its fixes. With the fixed framework, R2 and R4 need no change beyond the recomposition itself. The declarative chain was built after the fixes, so it shows only the fixed framework.
  • Line counts are non-blank lines of user source. They exclude the bundle and count the page's script tags.

Reproducing it

The experiment ran from a temporary directory, so this page carries the complete source. To rebuild it, lay the files out as the paths in the appendix show, under one directory, and add:

  • a symlink infusion to an infusion-6 checkout containing the framework fixes;
  • in react/, npm install react@18.3.1 react-dom@18.3.1 zustand@4.5.5 esbuild@0.19.12, then ./build.sh v0 and likewise for each React version;
  • a run of node run.js <version> <suite>, e.g. node run.js fluid/v4 normalised. The suites are base (v0), twoEditors (v1, v2), twoLayers (v3) and normalised (v4).

run.js loads infusion-6's demo runner and puppeteer by absolute path, so adjust those two paths to your checkout.
